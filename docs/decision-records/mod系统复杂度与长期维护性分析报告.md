## 摘要（结论先行）

**这个系统的真实复杂度已经明显超出"一个人 + AI 辅助"的舒适区，当前能维持主要靠两样东西：**
1. 反编译源码 `sts2src`（只读真相源）随时可查；
2. AI 会话的维护经验（skill + 大量"会话记录式"文档）承载了大量隐性知识。

**真正的三类高风险**（按不可控程度排序）：
1. **游戏本体更新**——外部触发、频率不可控，每次都可能打断全部字符串反射目标；
2. **PatchAll 单点故障**——96 个补丁类挂同一把锁，一个 `InvalidProgramException` 就全 mod 崩溃；
3. **无自动化测试**——迭代越密、功能越多，回归越靠人肉，且**已经出现"修 A 引入 B、再修 B 引入 C"的连锁**。

当前不应急于重构（风险高、收益低），**应先做"止血 + 建立覆盖清单 + 降低游戏更新成本"，把维护从"逐点考古"变成"按清单核对"**。详见第 6 节建议。

## 2. 复杂度来源分析

### 2.1 技术栈四层耦合（每层都是"非标准用法"）

```
┌─────────────────────────────────────────────────────────┐
│ ① Harmony 补丁层   96 类补丁，PatchAll 一次性全量加载     │
│   · 类级标记约定（缺失即静默跳过，已踩 2 次）              │
│   · 禁用 ref bool __runOriginal（InvalidProgramException）│
│   · 字符串方法名 / 反射 AccessTools 目标                  │
├─────────────────────────────────────────────────────────┤
│ ② 回环网络模拟层  LocalLoopbackHostGameService           │
│   · 伪实现游戏 INetHostGameService，NetId 可变            │
│   · 游戏多人同步器全部以为自己在真实联机                  │
├─────────────────────────────────────────────────────────┤
│ ③ 异步并发/串行化  AsyncLocal、SemaphoreSlim、           │
│                    全局选择器栈(PushSelector)、看门狗      │
│   · 手动编排"逻辑 owner"与"前台显示 owner"分离            │
├─────────────────────────────────────────────────────────┤
│ ④ Godot UI 注入层  原生子菜单/勾选框/滚动容器复刻、        │
│                    CallDeferred 时序依赖、节点可见性链     │
└─────────────────────────────────────────────────────────┘
```

关键点：**这不是"用游戏官方 mod API 写功能"，而是"在游戏内部实现上叠了四层非标准抽象"**。每一层都有自己的坑，且跨层交互（例如"补丁 A 里改 NetId → 选择器栈 → 异步链 → UI 刷新"）无法靠单一层的知识理解。

### 2.2 对游戏内部实现的深度依赖（更新即断）

- 编译期直接引用 `sts2.dll`（`LocalMultiControl.csproj` 的 `<Reference>`），成员改名 = 编译失败；
- **运行期字符串/反射目标**（`AccessTools`、`"SetupPlayerTurn"` 等具名方法、私有字段 `_localPlayerId`）改名 = **运行时静默失效**，编译不报错；
- 判断依据依赖反编译源码的行级细节（如 `CombatManager.cs:729 vs :772` 的时序）。
- 每次游戏更新，适配工作量 = 重新反编译（ilspycmd）→ 编译错修复 → **逐点核对字符串目标** → 实机回归。AGENTS.md §5 虽已固化成 playbook，但其中第 4 步"验证每个字符串目标"仍然是纯人工。

### 2.3 全局可变状态与隐式契约（心智负担最高处）

系统正确性依赖一组**极易破坏的全局隐式契约**：

| 隐式契约 | 破坏后果（均有实绩） |
|---|---|
| `LocalContext.NetId` == 回环 sender == 同步器 `_localPlayerId` 三处一致 | 奖励归属错位 → 事件软锁（坑 B，v1.38 刚修） |
| 切前台必须幂等、可回滚 | 切人后按钮状态陈旧 / 黑屏（多轮修复） |
| 全局选择器栈与异步作用域严格配对 | 真人选牌被抢答 / 后台选牌无人应答软锁 |
| 瓦库托管窗口不得跨过真人回合边界 | 弃牌/抽牌演出被吞（`CardPileAddForegroundContextPinPatch`） |
| 击杀动作必须走完才允许翻转战斗 | 空卡池崩溃 / 地图不跟投（坑 7，v1.37/1.38 连修三轮） |

这些契约**没有任何一处集中声明**，散落在各补丁的注释与 AI 会话记忆里。任何新补丁都可能无意违反某条契约。

### 2.4 功能膨胀：从"双人操作"到"AI 托管代理"

原项目定位是"让 1 人操控 2–12 个本地角色"。现在实际交付的已远超此：

- 瓦库托管：**13+ 个配置开关**、65 条药水规则表（双相位/意图伤害/角色路由/定向选牌器）、5 种选择器（Strategy/Smith/Targeted/Config/Form）、看门狗 + 超时安全网；
- 已设计未落地：聪明决策引擎（TurnContext 评分）、卡组感知抓牌、偏好记录器、SkadaHelper 决策链、CombatSolver 可插拔大脑接口（21.3）；
- 为第三方 mod（酒狐/古明地恋/水晶球/污浊药水）写了大量定向补丁。

**这意味着系统从"输入重路由工具"演进成了"半自主游戏代理"**，领域逻辑（什么药该喝、什么牌该打）与底层接入逻辑（怎么模拟网络、怎么切人）已经混在同一个代码库里。

### 2.5 知识资产：文档是"会话记录式"而非"系统化"

- 根目录 6 份可行性分析 = **决策过程的会话流水**（r1–r22 逐轮记录），不是架构文档；
- 真正的"坑"知识（7 份 skill references）放在 AI skill 目录——**对人工维护者基本不可见**；
- `docs/维护现状分析.md`（08-20）里的数据（98 文件）已过时（现 129 文件）；
- workshop 内容、版本号三处同步（根 json / workshop json / mod_manifest）历史上多次不一致。

### 2.6 多仓库并存

主仓库 + 4 个独立 fix 仓库，每个都重复 Entry / csproj / 构建 / 部署 / 字节校验流程。修复仓库的产物散落在不同 mods 槽位，出问题时排查链路横跨多个项目。

## 4. 已发生的"维护性事故"（实证，说明风险不是假设）

1. **`adae5aa` 整套补丁静默失效**：AI 修复提交了 4 个补丁类，全部只有方法级 `[HarmonyPatch]`，`PatchAll` 静默跳过——**修复实际从未生效**，靠后来加的 `GetPatchedMethods()` 统计日志才暴露。
2. **`CardSelectManualConfirmationPatch` 自加入起从未生效**：同类原因，潜伏极深。
3. **坑 7 连锁**：为修"击杀后战斗不结束"引入方案 A（立即胜利结算），结果触发空卡池崩溃；v1.37 改为延迟结算，又引入"打赢后奖励延迟最多 9 秒"；v1.38 再收紧到 600ms。**一个问题修了三轮**。
4. **探针类补丁也踩坑**：`NEndTurnButtonLifecyclePatch` 先是方法级-only 不触发，补上后又发现原版事件路径在本地多控下根本不触发——**探针本身证明"挂点选错"需要多次试错**。
5. **版本号/workshop 多处不同步**：v1.32 时根 json 已升 1.32.0 而 workshop/content 仍 1.31.0；`mod_id.txt` 写原条目、fork 条目另有其号。

这些事故的共同特征：**都是"无声失败"或"修 A 引 B"，在无测试环境下只能靠人肉逐轮发现**。

## 5. 综合判断

### 5.1 当前能维持的原因（不要破坏这些资产）

- 反编译参考源码 `sts2src` 可随时核对真相；
- 已有 `GetPatchedMethods()` 启动自检 + `dll_check.py` 字节校验 + marker 日志体系；
- skill + 文档沉淀了大部分已踩过的坑；
- 迭代虽密，但每次都有清晰 marker 和实机回归清单。

### 5.2 何时会"爆"（触发条件）

| 触发条件 | 后果 |
|---|---|
| 游戏本体发布新版本（尤其是大改多人/战斗模块） | R1+R3+R5 同时触发，适配周期可能以天计 |
| 新增大型功能（如 Phase 3/5 聪明决策） | R6 膨胀，补丁面持续扩大 |
| 更换维护 AI/人 | R7 知识断层，隐性契约全部丢失 |
| 同时维护多个分支 | 版本/文档/发布漂移概率上升 |

### 5.3 是否应该"重写/重构"

**不建议现在大重构。** 理由：
1. 系统行为正确性高度依赖对游戏内部时序的理解，重构 = 丢失这些隐式知识；
2. 无测试保障，重构必然引入大面积回归；
3. 该 mod 的目标游戏版本更新极快，重构成果很快又要重新适配。

**正确策略是"增加保护层 + 降低更新成本"，而不是动架构。**

## 6. 改进建议（按优先级）

### 6.1 短期（止血，1–2 周内可做）

| # | 建议 | 说明 |
|---|---|---|
| S1 | **建立"补丁目标覆盖清单"** | 一个 md（或工具生成）列出：每个补丁类 → 目标游戏方法（具名/字符串）→ 反编译源码锚点 → 已验证标志。借鉴 CombatSolver 的 `COMBAT_HOOK_COVERAGE.md` 方法论（21.4.2 #3）。游戏更新后按清单逐项核对，替代"编译错 + 记忆" |
| S2 | **启动自检升级** | 现有 `GetPatchedMethods()` 只打印部分方法。升级为：期望补丁目标清单（编译期维护）与实际 patched 列表比对，缺失即 `Log.Error` 高亮 |
| S3 | **把"游戏更新适配"脚本化** | 一个脚本：读 `release_info.json` → 跑 ilspycmd 重新生成 `sts2src` → 构建 → 打印全部字符串目标清单 → 自动 grep 新旧反编译源码差异。把 AGENTS.md §5 的第 2/4 步自动化 |
| S4 | **修文档漂移** | 更新 `docs/维护现状分析.md`；合并/归档根目录 8 份分析文档为"决策记录"单文件 + 架构文档；把 skill references 复制一份进仓库 `docs/`（人工维护者可读） |
| S5 | **修复仓库统一化** | 把 4 个 fix 小仓库合并进主仓库的 `Scripts/Fixes/` 或至少统一脚手架（一个构建脚本 + 统一部署槽位约定） |

### 6.2 中期（结构，一个月内）

| # | 建议 | 说明 |
|---|---|---|
| M1 | **给纯逻辑层开单元测试** | 瓦库规则表（65 药决策）、评分/决策函数、选择器策略、配置读写是纯 C# 逻辑，不依赖游戏运行时——用 `nunit` 建一个独立测试项目，引用 `sts2.dll` + 模拟桩。哪怕只覆盖决策函数，也能显著降低"改规则改坏"的概率 |
| M2 | **分层改造"最小侵入"** | 把瓦库领域逻辑（规则表/选择器/决策）与接入逻辑（NetId/sender/切前台）用接口隔开——这正是 21.3 已设计的 `IWakuuCombatBrain` 接口，落地时行为零变化，先建接口再搬实现 |
| M3 | **补丁隔离** | 评估把 PatchAll 拆成若干组（战斗/大厅/瓦库/UI），每组 try-catch，避免"瓦库新补丁崩 → 连本地多控都进不去" |
| M4 | **版本/发布自动化** | 一个脚本完成：三处版本号同步 → marker 生成 → 构建 → 拷贝 workshop/content → 生成 zip → 打印 SHA256。消除 R10 |

### 6.3 长期（架构方向）

| # | 建议 | 说明 |
|---|---|---|
| L1 | **降低字符串反射面** | 每次游戏更新时把能用具名方法/编译期引用的目标替换掉反射，仅保留无法避免的 |
| L2 | **领域逻辑外置** | 瓦库"大脑"（若 Phase 3/5 真落地）应做成独立模块或独立 mod，与本地多控核心解耦——参考 21.3.3 的 `WakuuBrain/*` 目录设计 |
| L3 | **建立 CI** | 即使不跑游戏，也可以做"构建 + 单元测试 + 补丁目标清单 diff"的 GitHub Actions，游戏更新后自动生成适配清单 |

## 7. 结论

1. **复杂度已过阈值**：129 文件 / 16.7k 行 / 96 补丁 / 四层非标准抽象 / 5 条全局隐式契约 / 6 个月 8 个版本——系统已从"mod"变成"一个运行在游戏进程内、伪装成联机会话的本地多控 + AI 托管平台"。
2. **短期风险可控**：因为有反编译源码 + skill + 文档 + 密集实机回归，当前运行状态是稳定的。
3. **真正不可控的变量是游戏本体更新**，其次是"知识连续性"（换人/AI 即断层）。
4. **推荐的行动顺序**：先做 S1–S5（止血与覆盖清单，低风险高回报）→ 再 M1–M4（测试与分层）→ 长期 L1–L3。**不要现在重写架构。**

> 一句话：**系统的复杂度不会自己消失，但可以通过"覆盖清单 + 自动化 + 测试"把它从"不可控的考古"变成"可控的核对"。**
