### 1.2 当前的"自动切换"共有两层

1. **回合循环强制切前台**（防止后台角色 UI/上下文错乱）：

2. **瓦库出牌前后的主动切视角**：

   - `RequestAutoSwitchToNonWakuuOncePerRound`（看完门狗跑完登记切回非瓦库）。

### 1.3 已经验证过的关键技术事实

### 需求一：【瓦库形态】遗物（替代低语耳环方案）—— ✅ 可行性高，大部分已存在

| 子项 | 结论 |

### 需求二：战斗内全量自动出牌 + 后台托管 —— ⚠️ 可行，但是本次改动中风险最高的部分

#### 2a. "确保所有出牌都能自动出"

- 现状硬上限 `MaxCardsToPlay = 13`（照抄原版 `WhisperingEarring.maxCardsToPlay = 13`）。改为"循环直到手牌无可出牌"，并加防死循环护栏（迭代上限 + 连续无进展熔断），**可行且低风险**。
- X 费卡：现有 `SpendResources()` 先扣光能量 + `AutoPlay(skipXCapture: true)` 的组合正确（X=实际花费），无需改。
- 出牌过程中衍生选择（发现/回收/选牌等）：由 `PushSelector(new VakuuCardSelector())` 作用域兜底，原版同机制，已验证。
- 手牌在循环中途增加（抽牌效果）：循环每轮重新查询手牌，天然覆盖。
- 主要熔断条件 `TryGetAutoplayUnsafeReason` 检查的是**前台** `NCombatUi.Hand.InCardPlay/IsInCardSelection`——后台化之后语义恰好变成安全护栏（真人正在拖牌时暂停瓦库出牌，看门狗稍后重试），保留即可。

#### 2b. "检测到瓦库形态就不切换过去，让它后台自动选"

**结论：可行，且有充分既有证据支撑，但有一处必须解决的硬缺口。**

依据：
- `CardCmd.AutoPlay` 主链路（sts2src `CardCmd.cs:51-131`）基本是模型层操作，UI 触点只有 `OnEnqueuePlayVfx`（可用 `skipCardPileVisuals: true` 跳过）与 `OnPlayWrapper` 内部动画；
- 1.3 节列出的四条既有事实（owner/前台分离、后台 EndTurn、敌方就绪补齐、同步禁用）都是已在实机验证过的。

需要的改动面：
1. `EnsureWakuuPerspective` 移除或旁路（不再切前台）；
2. 五个切前台补丁（`SetupPlayerTurn`/`DoTurnEnd`/`FlushPlayerHand`/`EnqueueHookAction`/`CardSelectForegroundSwitch`）增加 `IsWakuuEnabled(player.NetId)` 守卫——**注意守卫必须按 player 粒度，不能整体关掉**，否则影响真人的 Mini-Hakkero 等钩子选牌；
3. `RequestAutoSwitchToNonWakuuOncePerRound` 及相关"瓦库↔非瓦库"切换状态机可以大幅简化甚至退役（不再需要切回来）。

**硬缺口（最大风险点）：自动出牌作用域之外的瓦库交互式钩子。**
全局 `Selector` 只在自动出牌的 using 作用域内生效。瓦库在作用域外触发需要人选牌的效果（例如回合开始/结束遗物的 `FromHand` 选牌）时：
- 若无人切前台、又没有 selector → 给后台角色弹出选牌 UI 且永远没人点 → **软锁**。
- 候选对策：
  - **方案 1（推荐，混合式）**：仅在"瓦库 owner 的交互式 Hook 入队"这一种场景保留一次短暂切前台（即 `HookEnqueueForegroundPatch` 按 owner 是否瓦库决定放行或跳过），其余全部后台。改动最小、风险最低。
  - 方案 2：`EnqueueHookAction` 时若 owner 是瓦库，为该动作包一层临时 selector 作用域。技术上要精确对齐异步动作的生命周期，复杂度高。
  - 方案 3：瓦库存活期间挂持久低优先级 selector —— **否决**。selector 在所有 `From*` 路径中优先于 UI，会连真人玩家的选择一起吞掉。

**表现层残留风险**：后台角色的手牌 `NCard` 节点不存在于当前场景，出牌动画/VFX 相关代码若有未做空保护的路径可能抛异常。缓解：`AutoPlay(..., skipCardPileVisuals: true)` 参数现成；游戏代码普遍有 `?.` 保护；此项必须实机回归验证，属于"能做但要留足测试轮次"的部分。

### 需求三 a：战斗结束后自动领最左边的卡牌奖励 —— ✅ 可行，游戏留了现成口子

游戏源码给出了明确的自动化入口（sts2src `CardReward.cs:183-224 OnSelect`）：

```
if (LocalContext.IsMe(player)):
    if (_currentlyShownScreen != null):  num = await 屏幕等玩家点击
    else:                                num = Selector.GetSelectedCardReward(...)   ← 自动化路径
```

而 `NCardRewardSelectionScreen.ShowScreen` 只在 `TestMode.IsOn` 时返回 null（`NCardRewardSelectionScreen.cs:89-94`）——即"不弹屏 + 走 selector 作答"正是游戏测试模式的原生工作方式，我们只需局部复刻：

**实施方案**（在现有 `OfferMergedRewardsGeneratedOnceAsync` 展示奖励屏之前插入）：
1. 遍历合并奖励列表，找出归属瓦库角色的 `CardReward`（`Reward.Player` + `IsWakuuEnabled`，或按遗物判定）；
2. Prefix 补丁 `NCardRewardSelectionScreen.ShowScreen`：当"自动领奖上下文"激活时返回 null（不弹屏）；
3. 用 `ref Task __result` 包装模式（SKILL.md 坑 3）包住 `reward.SelectUnsynchronized()`：内部 `PushSelector(LeftmostSelector)`（`GetSelectedCardReward` 返回 `options.FirstOrDefault()` 即最左边，与原版 VakuuCardSelector 行为一致）；
4. 结算完成后把该奖励从展示列表移除 → 真人看到的奖励界面干净无干扰；
5. `SelectUnsynchronized` 绕过 `RewardsSetSynchronizer`——在本 mod 的单进程回环架构下安全（全员本地玩家，无远端分歧问题；mod 自己的 TestMode 分支就是这么干的）。

附带说明：
- "最左边"= `_cards[0]`；额外按钮类选项（变形等 RewardAlternative）默认不被 selector 选中，符合预期。
- 现有 `CardRewardPatch`（OnSelect 时换上下文到奖励归属者）与本方案正交共存。
- 金币/药水/遗物奖励不在本需求内，保持人工领取（如需扩展见待确认问题 1）。

### 需求三 b：非合作事件自动选最上面的选项 —— ⚠️ 可行，但实现路径要避开一个坑

- **合作事件判定现成**：`EventModel.IsShared` / `EventSynchronizer.IsShared`（投票制，全员投票后 host 抽签）。共享事件直接不碰，交给真人 —— 判定零成本。
- **坑**：不要走 `EventSynchronizer.ChooseLocalOption(index)` 来代选。它会把 `OptionIndexChosenMessage` 通过 `_netService.SendMessage` 发出去，同时本地立即执行 `ChooseOptionForEvent(LocalPlayer, index)`——单进程回环下消息还会被自己的 handler 再消费一次，存在**双重执行**风险；且它绑定的 `LocalPlayer` 是 synchronizer 构造时锁死的 `_localPlayerId`。
- **推荐路径**：直接操作瓦库玩家自己的 `EventModel` 实例：
  ```
  var ev = RunManager.Instance.EventSynchronizer.GetEventForPlayer(wakuuPlayer);
  while (!ev.IsFinished):
      opt = ev.CurrentOptions.FirstOrDefault(o => !o.IsLocked && !o.IsProceed)
      if (opt == null) break          // 复杂局面，留给真人
      await opt.Chosen()              // StateChanged → 界面自然刷新
  ```
  这与 UI 点击最终执行的 `eventOption.Chosen()`（`NEventRoom.OptionButtonClicked` → `ChooseOptionForEvent` → `Chosen()`）是同一落点，只是跳过消息层。
- **Proceed（离开事件）不自动点**：现有的"双角色都完成才允许 Proceed"拦截补丁（`NEventRoomOptionButtonPatch`）天然兼容——瓦库侧自动完成后，真人点 Proceed 即可直接走。
- **多页事件**（选完后出新选项）：上面的 while 循环天然覆盖。
- **必须设排除/中止规则**（否则有软锁风险）：
  - 会导致事件战斗的选项（`EnteringEventCombat`）；
  - 自定义小游戏事件（典型：水晶球 CrystalSphere——其完成回调要求 `owner == LocalContext.GetMe`，且 mod 为它修了三个软锁陷阱，绝不能自动乱选）；
  - 涅奥（Neow）开局奖励是否纳入自动化 → 见待确认问题 3。
  - 建议：一期用黑名单（按 `EventModel.Id` 或"选项触发战斗/小游戏即停"），命中即冻结该事件等真人处理。
- **触发时机**：进事件房后（现有 `NEventRoom.RefreshEventState` postfix 附近）延迟触发 + 重试；与 `RefreshEventRoomForControlledPlayer` 的按人重建流程（`UseSingleEventFlow=false`）兼容性需要实机验证。

### 需求四：概率记录 mod + 瓦库智能选择 —— ✅ 可行，工作量最大，建议独立分期

#### 数据采集（记录真人选择）
- 卡牌奖励：hook `CardReward.OnSelect` 的结果分支（已有 `CardRewardPatch` prefix/postfix 骨架可复用），记录 `{幕数(1/2/3), 首次/重复抓取, 三张候选卡的 key, 实际选择的 index}`。幕数可取 `runState` 当前层信息；候选 key 用排序后的卡牌 Id 串。
- 事件选项：hook `NEventRoomOptionButtonClicked`（真实点击才记录，天然排除瓦库代选），记录 `{eventId, 页码, 选项数, 选择的 index}`；`option.IsProceed` 的点击不计入。
- 排除瓦库：按 `reward.Player` / `event.Owner` 的 `IsWakuuEnabled` 过滤——现成 API。
- 存储：JSON 持久化（Godot `user://` 目录，即 `%APPDATA%\Godot\app_userdata\...` 下），启动时加载、每次记录即时写盘。技术上是普通文件读写，无风险。

#### 右下角概率显示（游玩中）
- 卡牌奖励屏：`NCardRewardSelectionScreen.RefreshOptions` 之后向 `_cardRow`/根 Control 注入一个小 Label（Godot 运行时 new Control + 设置锚点右下），mod 里已有同类先例（`NRewardButtonLabelPatch` 打角色标签、`LocalSimpleTextButton` 自绘按钮），**UI 注入路子已趟通**。
- 事件房：`Layout.AddOptions` 后同理注入。
- 显示内容：当前候选组合下每个选项的历史选择率（样本不足时显示"—"之类占位）。

#### 瓦库智能选择
- 领奖/选事件时查表：在该情境 key 下取历史选择率最高的项；并列最高按配置取"随机"或"最左"（一个常量开关的事）。
- 无记录时的兜底：退化为需求三的最左/最上策略。

#### 独立 mod vs 内置模块（重要决策点）
- 用户设想"另外写一个 mod"。技术上两种都可行：
  - **独立 dll mod**：需新的 mod id、json、ModInitializer。注意本机已有"id 冲突改名"教训（`DualRoleAdventurefixed`），新 mod 必须用全新 id；且与本 mod 有版本配套关系（读同一份概率表），发布时要联动。
  - **本 mod 内置模块 + 开关**（推荐）：部署/版本/日志排查都简单，概率功能用配置项启停，将来想拆随时能拆。
- 无论哪种，**记录器与瓦库智能选择的接口边界要清晰**（一张概率表 + 一个查询函数），方便日后拆分。

## 四、建议实施分期（每期独立分支 + marker 升位 + 实机回归）

**Phase 1 — 战斗托管完善（需求一 + 二）**
- 遗物更名【瓦库形态】+ 新描述文案（本地化注入三行）；
- 去 13 张上限、防死循环护栏；
- 后台化：移除 EnsureWakuuPerspective、五补丁加瓦库守卫（HookEnqueue 保留混合策略）、退役"每回合切回非瓦库"状态机；
- 持有瓦库形态时压制原版低语耳环的自动出牌钩子（保留 +1 能量，见 6.1）；
- **通用交互安全网**：交互超时检测 → 自动切前台 + 提示（见 6.4，后台化的前置保障，必须在同期落地）；
- 预计改动集中在 `LocalWakuuRelicRuntime` / `LocalMultiControlRuntime` / 两个 Foreground 补丁文件，量级中等，测试轮次主要花在后台表现回归与 6.5 回归清单。

**Phase 2 — 奖励与事件自动化（需求三 a/b）**
- 卡牌奖励：ShowScreen prefix + selector 作用域包装 + 合并列表预结算；
- 事件：非共享事件 while 循环直调 `Chosen()`，黑名单排除复杂事件；
- 量级中小，重点是事件边界的实机遍历。

**Phase 3 — 瓦库智能选择（需求四 + 九节启发式）**
- ~~自建记录器 → JSON 存储 → 右下角 UI 注入~~ **方案已升级：改用 SkadaHelper 社区统计数据源**（详见第八节），右下角统计显示由 SkadaHelper 自带；
- 本 mod 只需实现"决策时查表 + 回退策略"，量级大幅缩小；
- 智能选牌优先级（9.1/9.2：消耗/变化/删牌场景识别 + 优先级表）同期落地，与社区统计共用选择器上下文改造；

- 药水：写死规则的保守版（特定情况用原版药水，mod 药水随机）；

## 六、边界场景与第三方内容冲突分析（2026-08-24 增补二）

### 6.1 原版低语耳环 × 瓦库形态 同局共存

现状：`WhisperingEarringPatch` 目前是**无条件放行**的空 Prefix（`return true`），即瓦库角色若在局内又拿到了原版低语耳环（Ancient 稀有度，可获取），两个遗物的 `AfterAutoPrePlayPhaseEnteredLate` 都会触发。

冲突面分析：
- **第一回合双触发**：原版耳环最多自动打 13 张；瓦库形态循环打到无牌可出。先执行者把手牌打完后，后执行者查手牌为空自然空转退出——**不会死锁、不会重复出牌**；
- **选择器栈**：两处都是 `PushSelector` 的顺序 using 作用域，串行进出，无叠加冲突；
- **表现冗余**：可能出现双份瓦库台词（TalkCmd.Play）/双遗物闪光，纯观感问题；
- **能量叠加**：两个遗物的 `ModifyMaxEnergy` 各 +1，合计 +2 最大能量——数值膨胀属于玩法取舍，不是 bug。

**建议处理**：瓦库角色持有【瓦库形态】时，压制原版耳环的自动出牌钩子（**保留**其 +1 能量——那是另一个 hook，不受影响）。实现上给现有补丁加 `Player player` 参数 + `ref Task __result` 短路模式（SKILL.md 坑 2），条件命中返回 false。低风险小改动，纳入 Phase 1。

### 6.2 交互式选牌效果的通用判定规律

任何"需要玩家做选择"的效果，按实现管线分两类：

**A 类 —— 走游戏标准选牌管线 `CardSelectCmd.From*`**（FromSimpleGrid / FromHand / FromCombatPile / FromDeckForUpgrade / FromChooseACardScreen 等）：
- **在自动出牌作用域内**（全局 VakuuCardSelector 生效）：不弹 UI，自动按行优先取前 maxSelect 张解决。min/max 约束由管线自身校验（例如"15 张选至少 4 至多 15"→ `Take(15)` 取满即合法）；连 `RequireManualConfirmation`（需点确认的）也会被 selector 分支直接绕过（sts2src `CardSelectCmd.cs` 中 `else if (Selector != null)` 分支优先于确认逻辑）；
- **在作用域外**：正常弹 UI。若此时前台是非瓦库角色而选择归属者是后台瓦库 → 无人点击 → **软锁**。

**B 类 —— mod 自绘选择 UI，不走 CardSelectCmd**：我们的守卫完全看不见，无论前后台都可能卡住（注：这一风险在**当前版本的 mod 上同样存在**，并非本次改动引入）。

### 6.3 用户列举案例逐一归类

| 案例 | 管线推测 | 触发时机 | 初步判定与风险 |
| --- | --- | --- | --- |
| 古明地恋·弹幕的墨迹测试（15 张选 ≥4 ≤15 后确认） | 待实机验证；若是自绘 UI 则 B 类 | 出牌结算中 | A 类则作用域内自动全取 15 张（约束合法），语义是否合意看效果本身；B 类则依赖安全网兜底 |
| 古明地恋·DNA 的瑕疵（强制结束恋的本回合，下回合恋与玩家都可出牌，恋也从左到右出牌） | 非选牌类 | 回合结构变化 | 恋的自主出牌由该 mod 自管；**需实测**：它的出牌与我们的看门狗/动作队列交错是否会互相打断，以及"同侧双行动者"是否触发我们切人状态机的误判 |
| 古明地恋·封闭心灵（结束恋的回合 + 要求玩家从牌组选一张永久升级） | A 类（FromDeckForUpgrade 特征吻合） | 恋的回合结束时 | 发生在自动出牌作用域外；若被要求选择的是后台瓦库玩家 → 软锁风险点，靠安全网/混合切换兜底 |
| 东方先古之民·非想天则（战斗开始时 10 张故障机器人卡选 5） | A 类（大概率 FromSimpleGrid） | **战斗开始**（必定在自动出牌作用域之外） | **高风险典型案例**：开局选择若归属后台瓦库必软锁。是"混合策略/安全网"必要性的最有力论据 |
| 观者 mod·预见（从看到的抽牌堆顶决定弃哪几张） | A 类（FromCombatPile 特征吻合） | 出牌中 | 作用域内自动取前 N 张——功能可用但"弃哪些"的语义未必理想；可接受或后续针对性优化 |

共性结论：**用户列的案例全部落在 6.2 的框架内**，没有超出"作用域内自动解决 / 作用域外软锁"的二分法。真正要新做的是下面的安全网。

### 6.4 通用交互安全网（新增设计，建议并入 Phase 1）

后台化之后必须有的兜底机制：

```
触发条件（同时满足）：
  1. NOverlayStack 存在等待玩家输入的屏幕/弹层
  2. 该交互的归属上下文可判定为瓦库玩家（能判则精确判；判不了按保守处理）
  3. 无任何输入持续超过阈值 T 秒
动作：
  → 自动把前台切给该瓦库玩家 + 全屏提示"瓦库遇到需要手动处理的界面"
  → 打高亮日志
效果：把硬软锁降级为"请人工点一下"，同时覆盖 A/B 两类（B 类只有这条能兜住）
```

- 与现有 watchdog/熔断日志体系共用去重键，避免刷屏；
- 阈值 T 建议 8–15 秒（太短会在正常动画期间误报，配合 6.2 的 CanSwitch 守卫防误切）；
- 无法精确判归属时宁可误切到瓦库（人工可见）也不静默卡死。

### 6.5 新增实机回归清单

1. 双遗物局：瓦库形态 + 原版耳环同持，验证第一回合只触发一次接管、+2 能量生效、无双台词（压制生效后应为零原版钩子）；
2. 墨迹测试：瓦库打出该卡 → 观察 15 张是否被自动选取、效果正确入栈；
3. DNA 的瑕疵：瓦库场上有恋 → 连续两回合观察恋与瓦库的出牌交错、无队列死等；
4. 封闭心灵：恋回合结束后升级选牌界面归属判定与弹出行为；
5. 非想天则：带瓦库进战斗 → 开局 10 选 5 是否触发安全网切人提示；
6. 预见：作用域内的弃牌自动决策是否符合最低可玩性；
7. 安全网本身：人为制造一个 B 类弹层（如某 mod 自定义界面），验证超时切人与提示出现、处理后流程继续。

### 6.6 同侧多行动者（古明地恋）与瓦库的出牌权竞争

用户追问："恋和瓦库抢出牌不用管吗"。分层回答：

**已有隔离（无需处理的部分）**：
- 自动出牌循环只遍历 `PileType.Hand.GetPile(relic.Owner)` —— **瓦库形态永远不会替恋出牌**；
- 恋的自主出牌（含她的"从左到右"）由该 mod 自行驱动，与我们不共享决策代码。

**真实竞争面（需要设计应对的部分）**：

| 竞争点 | 表现 | 对策 |
| --- | --- | --- |
| 动作队列交错 | 恋的行动与瓦库自动出牌在同一 PlayPhase 内并发入队，可能交错执行或互相等待 | 实测为主（回归清单 #3）；现有 SelectorScopeGate 串行闸门已有一定保护 |
| 回合结构抖动 | DNA 的瑕疵等强制结束/追加行动者的效果，使熔断条件（CurrentSide/PlayPhase 检查）反复翻转 → 看门狗反复重试 | 看门狗冷却/去重键已有；必要时把"结构异常"计入熔断 |
| 时机窗口抢占 | 全自动秒出可能跳过恋的效果所依赖的玩家先行操作 | 见下面的降级开关 |

**新增降级开关（非默认行为）**："检测到非标准行动者在场（恋等）时，暂停看门狗重启、只保留回合开始的一次性接管"——把节奏交还原时序，作为实测发现抢牌问题后的逃生门。并入 6.4 的开关体系。

## 八、SkadaHelper 集成分析（2026-08-24 增补）

> 背景：创意工坊已有「皮皮军师: SkadaHelper」(v0.8.7, workshop id 3763804482)，
> 内置 404,569 局 v0.107 实战统计快照 + 本地路线模型，纯显示层 mod。
> 已反编译其 DLL 验证集成面（反编译产物在临时目录，不入库）。

### 8.1 公开 API 面（已验证可直接调用）

| 类型 | 可见性 | 说明 |
| --- | --- | --- |
| `SkadaHelper.Scripts.Lite.DataProvider` | **public static class** | 数据入口 |
| `DataProvider.Data` | **public static** `BundleData?` | 当前生效的已校验数据包（缓存→内置→在线刷新） |
| `BundleData.GetCharacter(charId)` / `.GetCard(charId, cardId)` | public | 角色包查询 |
| `CharacterBundle.GetCard(cardId)` | public | → `CardStats`；自动按进阶(A7+)/单人多人切片并逐级回退 |
| `CharacterBundle.GetEvents(eventId)` | public | → `List<EventOptionStats>`；eventId 大写 |
| `CardStats` 字段 | public | `PickRate / WinRate / WinRateSkipped / WinRateHeld / OfferCount / PickedCount / SkippedCount` + 升级、删牌统计（位置/次数/首次胜率） |
| `EventOptionStats` 字段 | public | `Text / Count / WinRate` |

关键实现细节（来自反编译）：
- 卡牌 key = 裸卡 id（自动剥 `+` 升级后缀）；角色 key = `ModelId.Entry` 大写；
- 单人/多人切片判定是 `Players.Count <= 1` —— **本 mod 双人模式会命中 multi 切片**（数据来自线上真人合作局，语境略有偏差但可接受）；
- 切片回退链：当前进阶切片(≥A7) → 全量；multi/solo → 全量。查询永远有兜底值。

### 8.2 推荐集成方式

- **可选依赖 + 反射查询**：`AccessTools.TypeByName("SkadaHelper.Scripts.Lite.DataProvider")` → 读静态属性 `Data`。未安装/未加载时优雅回退到"最左/最上"策略。不做编译期引用（它是可选第三方 mod）。
- **用瓦库玩家自己的角色查表**：不要走它的 `LiteGameContext.CurrentCharacterId`（跟随前台 `LocalContext.GetMe()`，在多控下语义漂移）；直接 `BundleData.Characters[wakuuCharId]` 或 `GetCharacter(wakuuCharId)`。
- **决策信号建议**：
  - 卡牌奖励：主信号 `PickRate`，可选加权 `WinRateHeld - WinRateSkipped`（近似因果增益）；样本量 `OfferCount` 过小则视为无数据；
  - 事件选项：`WinRate` 最高且 `Count` 达阈值者；并列最高走用户开关（默认最左）。

### 8.3 相比原自建记录器方案的优势

1. **样本量碾压**：40 万局社区数据 vs 个人几百次选择，冷启动即有效；
2. **自带胜率维度**：不只是"别人选什么"，还有"选了之后赢没赢"，比纯选择率更强的信号；
3. **零开发量的右下角显示**：SkadaHelper 本身就在卡牌奖励/事件/商店/删牌升级界面渲染统计面板——原需求四的"游玩过程中右下角显示概率"直接由它满足；
4. **别人维护**：随版本更新数据口径，本 mod 不背数据管道包袱。

### 8.4 风险与限制

| # | 风险 | 等级 | 对策 |
| --- | --- | --- | --- |
| 1 | 数据口径 v0.107 vs 当前游戏 v0.111，元环境漂移 | 中 | 接受（作者更新后自动恢复）；决策仅作参考信号，不改变回退策略的正确性 |
| 2 | 事件选项按**文本模糊 Contains 匹配**，语言敏感：若数据集为英文而玩家中文界面，可能匹配失败 | 中 | 实机验证中文环境命中率；未命中时回退最上选项 + 打日志统计命中率 |
| 3 | multi 切片来自线上真人合作局，与本地单人多控语境有偏差 | 低 | 接受；必要时只取全量切片 |
| 4 | 第三方 mod 可能改内部结构（类名/属性名） | 低 | 反射全部集中在单一适配器文件 + 启动探测日志；失效即静默回退 |
| 5 | 合规 | 低 | 只读消费内存中公开 API，不重分发其 dll/数据，不修改其行为；AGENTS.md 的"不改第三方 dll"约束不受影响 |
| 6 | **不含任何 mod 内容**（已反编译确认：`BundleFilters` 仅含版本/进阶/模式/人数四个维度，卡表/事件表为纯原版 id 字典；标准模式数据源决定了 mod 卡牌/事件无 key） | 中 | 查询 miss 一律返回 null → 静默回退最左/最上（无害降级）；mod 环境下原版卡的社区统计参考价值也会稀释，接受其仅为参考信号 |

### 8.4.1 mod 内容缺口的应对：三级决策链

个人偏好记录器（用户设想的 STS1 抓率统计式 mod，可做独立 dll）与本方案**互补而非二选一**——它记录本机实际对局，天然覆盖 mod 卡牌与 mod 事件：

```
① 个人记录器（该情境有足够样本时，最贴合实际环境含 mod 内容）
② SkadaHelper 社区统计（原版内容，大样本）
③ 兜底策略（最左 / 最上，按已定开关）
```

### 8.5 与本 mod 补丁的共存性（已核对双方补丁面）

- SkadaHelper 的补丁全是 **postfix 显示层**（`NCardRewardSelectionScreen.RefreshOptions`、`NEventLayout.AddOptions`、商店/地图/牌组网格），不改游戏状态；
- 本 mod 计划对瓦库奖励**不弹屏**（ShowScreen prefix 返回 null）→ 它的 RefreshOptions postfix 对这些屏自然不触发，互不干扰；
- 事件自动化直调 `EventOption.Chosen()`，不经过 `NEventLayout.AddOptions` 路径 → 无冲突；
- 双 Harmony 同进程共存是常规场景，无风险。

### 8.6 结论

**采纳**：Phase 3 主路径改为"三级决策链"——个人记录（可选，后建）→ SkadaHelper 社区统计 → 最左/最上兜底。SkadaHelper 不支持 mod 内容的限制由兜底策略与个人记录器共同覆盖；原需求四的开发量缩减约七成。

## 九、聪明瓦库：启发式决策升级（2026-08-24 增补三）

> 用户需求原文归纳：
> 1. 消耗类选牌：优先 诅咒 → 状态 → 任务 → 打击 → 防御，再从左到右；
>    复制类选牌：尽量排除这些牌（优先选其余更好的牌），候选全是这类时按倒序 防御 → 打击 → 任务 → 状态 → 诅咒；
> 2. 变化类选牌：优先 打击 → 防御，尽量避开 诅咒/状态/任务；
> 3. 商店：买胜率高的东西、删诅咒/打击/防御；
> 4. 所有瓦库行为加独立开关。
>
> 用户自评"结果还是会打得很烂"——目标是"不犯低级错误"而非最优。

### 9.1 选牌场景识别——关键可行性依据

游戏源码中选牌入口天然可分类（sts2src `CardSelectCmd.cs`），无需猜测 UI 语义：

| 场景 | 游戏管线 | 识别难度 |
| --- | --- | --- |
| 变化（Transform） | `FromDeckForTransformation` —— **专用方法** | ★ 直接按方法区分 |
| 删牌（商店/事件） | `FromDeckForRemoval` —— **专用方法** | ★ 直接按方法区分 |
| 升级 | `FromDeckForUpgrade` —— 专用方法 | ★ |
| 消耗/弃置/复制等手牌与杂项选择 | `FromHand` / `FromSimpleGrid` / `FromChooseACardScreen`（带 `source` 来源模型参数与 prefs 标题 LocString） | ★★ 按 `source` 的类型名 / prefs 标题 loc key 分类；未知来源回退通用策略 |

实现载体：把现在的 `VakuuCardSelector`（无脑取最左）升级为**带场景上下文的优先级选择器**——在自动出牌作用域内拦截所有 `GetSelectedCards` 调用，先判定场景类别再套对应优先级表。

### 9.2 优先级规则表（可配置）

```
场景 = 消耗/删除类（去掉坏牌）:
    Curse > Status > Quest > Strike > 基础防御 > 其余从左到右
场景 = 复制类（复制好牌）:
    首选：非 {Curse/Status/Quest/Strike/基础防御} 的牌，从左到右
    候选全为上述类型时：倒序 防御 > 打击 > 任务 > 状态 > 诅咒
场景 = 变化类（变掉平庸牌、保留特殊牌）:
    Strike > Defend > 其余从左到右；硬排除 Curse/Status/Quest
兜底: 现行"最左"
```

> 实现说明：规则做成数据驱动的优先级表（JSON 或代码常量），每条场景一行即可调整，不影响结构。"候选全是坏牌时倒序"的判定就是普通过滤后集合是否为空，无额外成本。

卡牌类型判定 API：`CardModel.CardType`（Curse/Status/Quest/Attack/Skill）+ 卡 id 白名单（打击/防御的各角色变体如 Strike_Ironclad 需按 `BareCardId` 前缀匹配）。均为公开模型属性，零风险。

### 9.3 商店自动化

## 十八、Phase 5 设计：聪明瓦库决策器（局内打牌 + 卡组构造感知抓牌）（2026-08-27）

### 18.1 现状差距

当前出牌循环（`LocalWakuuRelicRuntime.ExecuteBeforePlayPhaseStartAsync`，:207-238）的策略为：

```csharp
// 每次迭代取手牌中第一张能打的牌
CardModel? card = PileType.Hand.GetPile(relic.Owner)
    .Cards.FirstOrDefault(candidate => candidate.CanPlay());
```

### 18.2 局内打牌决策器

#### 18.2.1 可用信息源（已从反编译确认全部公开可读）

#### 18.2.3 阶段 A：场面评估——TurnContext

每回合（自动出牌循环入口处）一次性计算：

```csharp
internal readonly struct TurnContext
{
    public readonly int PlayerHp;           // 瓦库当前血量
    public readonly int PlayerMaxHp;        // 瓦库最大血量
    public readonly int PlayerBlock;        // 当前格挡
    public readonly int Energy;             // 本回合能量
    public readonly int TotalEnemyThreat;   // 所有敌人下回合攻击意图总伤害
    public readonly int LethalThreshold;    // 瓦库致死线（HP - Block）
    public readonly bool IsLethalDanger;    // 敌方总伤害 ≥ 致死线
```

#### 18.2.4 阶段 B：卡牌评分函数

每张手牌在每轮迭代前被评分，评分范围 0–100：

```csharp
internal static int ScoreCard(CardModel card, TurnContext ctx, Player player)
{
    int score = 0;

    // ── 基础分（卡牌类型权重）──
    score += card.Type switch
    {
        CardType.Power  => 50,   // Power 永久增益，尽早打出
        CardType.Attack => 30,
        CardType.Skill  => 35,   // Skill 包含格挡/增益，通常优先于攻击
        _               => 10,
    };

    // ── 能量效率 ──
    int cost = card.EnergyCost.GetAmountToSpend();
    if (cost == 0)
        score += 15;  // 0 费牌几乎总是该打
    else if (cost <= 1)
        score += 5;
    // X 费牌：见特殊处理

    // ── 场景修正 ──
    score += ContextModifier(card, ctx, player);

    // ── 关键词修正 ──
    if (card.Keywords.Contains(CardKeyword.Exhaust))
        score -= 5;   // 消耗牌用后永久移除，谨慎打
    if (card.Keywords.Contains(CardKeyword.Ethereal))
        score += 10;  // 虚无牌不打就消失，倾向打出
    if (card.Keywords.Contains(CardKeyword.Retain))
        score -= 8;   // 保留牌可以留到更好的时机

    return Math.Max(score, 0);
}
```

**场景修正（`ContextModifier`）—— 核心智能所在：**

```csharp
private static int ContextModifier(CardModel card, TurnContext ctx, Player player)
{
    int mod = 0;

    // ── 防御优先：血量危险时大幅加分 ──
    bool needsDefense = ctx.IsLethalDanger || (float)ctx.PlayerHp / ctx.PlayerMaxHp < 0.5f;
    if (needsDefense && card.GainsBlock)
    {
        int estimatedBlock = EstimateBlock(card, player);
        mod += 30;                              // 基础防御加分
        mod += Math.Min(estimatedBlock, 20);    // 格挡量越高分越高（封顶 20）
    }

    // ── 攻击优先：有击杀窗口时 ──
    if (ctx.KillableEnemyIndex >= 0)
    {
        if (card.Type == CardType.Attack)
        {
            int estimatedDamage = EstimateDamage(card, player);
            mod += 20;                          // 攻击加分
            if (estimatedDamage >= ctx.KillableEnemyHp)
                mod += 40;                      // 能击杀：极高加分（消除威胁）
        }
    }

    // ── 第一回合：Power 牌额外加分 ──
    if (ctx.RoundNumber <= 1 && card.Type == CardType.Power)
        mod += 20;  // 早铺永久增益是基本功

    // ── AoE 价值：多敌人时 AoE 牌加分 ──
    if (ctx.EnemyCount >= 2 && card.TargetType == TargetType.AllEnemies)
        mod += 15 + (ctx.EnemyCount - 2) * 5;  // 每多一个敌人多 5 分

    // ── 集火价值：单体牌对低血敌人加分 ──
    if (card.TargetType == TargetType.AnyEnemy && ctx.KillableEnemyIndex >= 0)
        mod += 10;  // 鼓励集火可击杀目标

    // ── 能量富余时倾向打贵牌 ──
    int cost = card.EnergyCost.GetAmountToSpend();
    if (ctx.Energy >= 4 && cost >= 3)
        mod += 10;  // 大费牌在能量充足时值得打

    return mod;
}
```

**伤害/格挡预估函数（简化版，不走完整 Hook 管线）：**

```csharp
private static int EstimateDamage(CardModel card, Player player)
{
    // 读取卡牌基础伤害值
    if (card.DynamicVarSet?.Damage == null) return 0;
    int baseDamage = (int)card.DynamicVarSet.Damage.BaseValue;

    // 加力量
    int strength = player.Creature.GetPowerAmount<StrengthPower>();
    int damage = baseDamage + strength;

    // 简化倍率（不区分目标易伤/虚弱，仅作粗估）
    return Math.Max(damage, 0);
}

private static int EstimateBlock(CardModel card, Player player)
{
    if (card.DynamicVarSet?.Block == null) return 0;
    int baseBlock = (int)card.DynamicVarSet.Block.BaseValue;
    int dexterity = player.Creature.GetPowerAmount<DexterityPower>();
    return baseBlock + dexterity;
}
```

> **精度取舍说明：** 上述预估忽略了附魔（Enchantment）、遗物修正、全局 Hook 等中间层——完整管线需模拟 `Hook.ModifyDamage()` 的全部 4 阶段（附魔加/乘 → 力量加 → 易伤虚弱乘 → 上限截断）。一期用简化版已足以区分"该打攻击还是格挡"的粗粒度决策；若后续发现精度不够（如大量附魔/遗物修正场景），可升级为调用 `card.UpdateDynamicVarPreview(CardPreviewMode.Play, target, null)` 读取游戏自带的预览值——该方法已是公开 API，无副作用，不实际出牌。

```csharp
private static Creature? ResolveTarget(CardModel card, ICombatState combatState, Player owner)
{
    switch (card.TargetType)
    {
        case TargetType.AnyEnemy:
            return ResolveBestEnemyTarget(combatState, owner);
        case TargetType.AnyAlly:
            // 给真人角色增益时优先真人（而非随机）

        case TargetType.AnyPlayer:
            return owner.Creature;
        default:
            return null;

}

private static Creature? ResolveBestEnemyTarget(ICombatState combatState, Player owner)
{
    var enemies = combatState.HittableEnemies.ToList();
    if (enemies.Count == 0) return null;

    int estimatedDamage = EstimateDamageOfCurrentCard(owner);  // 上下文传入

    // 优先 1：能击杀的敌人
    var killable = enemies.FirstOrDefault(e =>
        (e.CurrentHp - e.Block) <= estimatedDamage);
    if (killable != null) return killable;

    // 优先 2：血量最低的敌人（集火）
    return enemies.OrderBy(e => e.CurrentHp - e.Block).First();
}
```

### 18.3 卡组构造感知抓牌

#### 18.3.1 问题定义

当前抓牌（卡牌奖励自动领 + 事件选牌）策略：

- 卡牌奖励：无脑取最左（`VakuuCardSelector` 行优先 / `autoClaimCards` 领最左）
- 事件选牌：最上（`eventChoiceMode: first`）
- SkadaHelper 社区统计（Phase 3 计划，尚未实装）：按 PickRate / WinRate 最高者选

**缺陷：** 这些策略都是"这张牌好不好"的孤立评估，不看"我的牌组现在缺什么"。例如：
- 牌组已有 8 张攻击、2 张防御 → 继续抓攻击牌即使胜率高，但牌组失衡容易暴毙
- 牌组没有任何产能量牌 → 抓一张 3 费牌虽然强但打不出去
- 牌组需要删打击/防御来精简 → 手动删牌场景已有 9.2 的消耗优先级，但抓牌时也应考虑"这张牌值不值得加入"

#### 18.3.2 卡组构成分析器（`DeckCompositionAnalyzer`）

**运行时机**：每次需要做抓牌/选牌决策时（非每回合，仅在卡牌奖励/事件选牌/商店买牌时），一次性扫描 `player.Deck.Cards`（run 级全牌组）。

```csharp
    public readonly int EnergyGenCount;       // 产能量牌数（关键词/效果判定）
    public readonly int DrawCount;            // 抽牌牌数
    public readonly float AttackRatio;        // 攻击占比
    public readonly float SkillRatio;         // 技能占比
    public readonly float BadCardRatio;       // 垃圾牌占比（打击+防御+状态+诅咒）
```

**构成分析逻辑**：

```csharp
internal static DeckProfile Analyze(Player player)
{
    var cards = player.Deck.Cards.ToList();
    int total = cards.Count;

    int attacks = cards.Count(c => c.Type == CardType.Attack);
    int skills  = cards.Count(c => c.Type == CardType.Skill);
    int powers  = cards.Count(c => c.Type == CardType.Power);
    int status  = cards.Count(c => c.Type == CardType.Status);
    int curses  = cards.Count(c => c.Type == CardType.Curse);

    // 基础牌按 ID 匹配（复用 RestAutoChoice.IsBasicStrikeOrDefend）
    int basicStrikes = cards.Count(c => c.Id.Entry.ToUpperInvariant().Contains("STRIKE"));
    int basicDefends = cards.Count(c => c.Id.Entry.ToUpperInvariant().Contains("DEFEND"));

    // 产能量牌：按关键词/ID 白名单（战斗姿态、发现、祭品等产能量效果）
    int energyGen = cards.Count(c => HasEnergyGenerationEffect(c));

    // 抽牌牌：按关键词/ID 白名单
    int drawCards = cards.Count(c => HasDrawEffect(c));

    return new DeckProfile(
        total, attacks, skills, powers, status, curses,
        basicStrikes, basicDefends, energyGen, drawCards,
        attackRatio: total > 0 ? (float)attacks / total : 0f,
        skillRatio:  total > 0 ? (float)skills  / total : 0f,
        badCardRatio: total > 0 ? (float)(basicStrikes + basicDefends + status + curses) / total : 0f
    );
}
```

> **产能量/抽牌牌的判定**：STS2 的卡牌效果全写在 `OnPlay` 里，没有通用的"效果标签"。一期用 **ID 白名单**（如 `ENERGY_GENERATION_CARDS = ["Bloodletting", "DarkstonePeriapt", ...]`，`DRAW_CARDS = ["WaveOfTheHand", ...]`），后续可扩展为关键词扫描或维护一个不断增长的列表。

#### 18.3.3 卡组需求评估（`DeckNeedEvaluator`）

基于 `DeckProfile` 输出一组需求向量：

```csharp
internal readonly struct DeckNeeds
{
    public readonly NeedLevel BlockNeed;      // 需要更多防御
    public readonly NeedLevel AttackNeed;     // 需要更多攻击
    public readonly NeedLevel PowerNeed;      // 需要更多能力
    public readonly NeedLevel EnergyNeed;     // 需要产能量
    public readonly NeedLevel DrawNeed;       // 需要抽牌
    public readonly NeedLevel ThinningNeed;   // 需要精简（删牌）
}

internal enum NeedLevel { None, Low, Medium, High }
```

**判定规则**：

```csharp
internal static DeckNeeds Evaluate(DeckProfile profile)
{
    var needs = new DeckNeeds();

    // 攻防比例失衡判定
    float idealAttackRatio = 0.45f;   // 理想攻击占比 45%
    float idealSkillRatio  = 0.40f;   // 理想技能占比 40%
    float tolerance = 0.10f;          // 容忍偏差

    if (profile.AttackRatio < idealAttackRatio - tolerance)
        needs.AttackNeed = NeedLevel.High;
    else if (profile.AttackRatio < idealAttackRatio)
        needs.AttackNeed = NeedLevel.Low;

    if (profile.SkillRatio < idealSkillRatio - tolerance)
        needs.BlockNeed = NeedLevel.High;
    else if (profile.SkillRatio < idealSkillRatio)
        needs.BlockNeed = NeedLevel.Low;

    // 能力牌太少（前 3 幕通常需要至少 2-3 张能力牌来叠层）
    if (profile.PowerCount == 0)
        needs.PowerNeed = NeedLevel.High;
    else if (profile.PowerCount <= 2)
        needs.PowerNeed = NeedLevel.Low;

    // 产能量不足（牌组 > 15 张但产能量 < 2）
    if (profile.TotalCards > 15 && profile.EnergyGenCount < 2)
        needs.EnergyNeed = NeedLevel.Medium;

    // 抽牌不足
    if (profile.TotalCards > 15 && profile.DrawCount < 2)
        needs.DrawNeed = NeedLevel.Medium;

    // 垃圾牌占比过高（> 35% 需要删牌）
    if (profile.BadCardRatio > 0.35f)
        needs.ThinningNeed = NeedLevel.High;
    else if (profile.BadCardRatio > 0.25f)
        needs.ThinningNeed = NeedLevel.Medium;

    return needs;
}
```

#### 18.3.4 抓牌评分函数（`DraftEvaluator`）

将候选牌与卡组需求匹配打分：

```csharp
internal static int ScoreCandidate(CardModel candidate, DeckProfile profile, DeckNeeds needs)
{
    int score = 0;

    // ── 基础分：SkadaHelper 社区统计（可选数据源） ──
    score += GetCommunityScore(candidate);   // Phase 3 三级决策链的第 ② 级

    // ── 类型需求修正 ──
    score += candidate.Type switch
    {
        CardType.Attack when needs.AttackNeed >= NeedLevel.Medium => 20,
        CardType.Attack when needs.AttackNeed == NeedLevel.Low   => 5,
        CardType.Skill  when needs.BlockNeed  >= NeedLevel.Medium => 20,
        CardType.Skill  when needs.BlockNeed  == NeedLevel.Low   => 5,
        CardType.Power  when needs.PowerNeed  >= NeedLevel.Medium => 25,
        CardType.Power  when needs.PowerNeed  == NeedLevel.Low   => 10,
        // 攻击饱和时攻击牌减分
        CardType.Attack when profile.AttackRatio > 0.55f => -15,
        // 技能饱和时技能牌减分
        CardType.Skill  when profile.SkillRatio  > 0.55f => -15,
        _ => 0,
    };

    // ── 能量可行性修正 ──
    int cost = candidate.EnergyCost.Canonical;
    if (needs.EnergyNeed >= NeedLevel.Medium && cost >= 3)
        score -= 10;  // 缺产能量时高费牌打折

    // ── 产能量/抽牌牌特殊加分 ──
    if (HasEnergyGenerationEffect(candidate) && needs.EnergyNeed >= NeedLevel.Medium)
        score += 15;
    if (HasDrawEffect(candidate) && needs.DrawNeed >= NeedLevel.Medium)
        score += 15;

    // ── 基础牌惩罚（打击/防御通常不值得抓） ──
    string id = candidate.Id.Entry.ToUpperInvariant();
    if (id.Contains("STRIKE") || id.Contains("DEFEND"))
        score -= 20;

    // ── 状态/诅咒牌惩罚（不应该主动抓） ──
    if (candidate.Type is CardType.Status or CardType.Curse)
        score -= 50;

    // ── 牌组规模修正（牌组已经很大时减少抓牌倾向） ──
    if (profile.TotalCards > 25)
        score -= 5;
    if (profile.TotalCards > 35)
        score -= 10;

    return score;
}
```

### 18.7 风险评估

| # | 风险 | 等级 | 缓解 |
| --- | --- | --- | --- |
| 1 | 评分函数调参不当导致比无脑最左更差 | 中 | `smartCombat` 开关默认开但可关；初期评分偏保守（宁可不加分也不乱减分），实机观察后调参 |

| 10 | 偏好记录文件膨胀（JSON 越来越大） | 低 | 上限 5000 条 + 启动时按指纹清理过期 + 按时间戳淘汰最旧；实测单条 ~200 字节，5000 条 ≈ 1MB |

### 18.8 mod 卡兼容性分析与对策

#### 18.8.1 三个兼容性缺口

**缺口 1：`DynamicVar.Damage.BaseValue` 读取失败（打牌评分核心受影响）**

STS2 的 mod 卡继承 `CardModel`，但其数值系统可能绕过 `DynamicVar`：

- 原版卡：`DamageVar(6, DamageProps.card)` 在构造时声明 → `DynamicVarSet.Damage` 非 null
- 某些 mod 卡：直接在 `OnPlay` 里硬编码伤害（`CreatureCmd.Damage(8, ...)`），不声明 `DamageVar` → `DynamicVarSet.Damage` 为 null → `EstimateDamage` 返回 0

**影响**：评分函数无法知道这张牌的伤害量 → 击杀窗口判定失效（本该打的牌被低排）、防御优先误判（把攻击牌当 0 分）。

**缺口 2：产能量/抽牌白名单不含 mod 卡**

`HasEnergyGenerationEffect` / `HasDrawEffect` 按原版 ID 白名单匹配。东方 mod 的产能量牌（如某些角色的"力量"或"蓝魂"机制）不在列表里。

**影响**：抓牌时 mod 的产能量/抽牌牌不被加分，缺能量时漏抓。

**缺口 3：SkadaHelper 无 mod 内容**

已确认（8.4.1 第⑥条）：社区统计不含 mod 卡牌。mod 卡在三级决策链的第②级永远 miss。

**影响**：抓牌时 mod 卡没有社区统计分，退化到兜底——本身无害但浪费了可用信息。

#### 18.8.2 对策：推断层 + 运行期学习

**对策 1：`EstimateDamage` 推断层（解决缺口 1，最高优先）**

在 `DynamicVar` 读 null 时，增加基于卡牌类型和费用的推断兜底：

```csharp
private static int EstimateDamage(CardModel card, Player player)
{
    // 路径 A：有 DynamicVar，直接读（原版卡 + 声明了变量的 mod 卡）
    if (card.DynamicVarSet?.Damage != null)
    {
        int baseDamage = (int)card.DynamicVarSet.Damage.BaseValue;
        int strength = player.Creature.GetPowerAmount<StrengthPower>();
        return Math.Max(baseDamage + strength, 0);
    }

    // 路径 B：无 DynamicVar，按类型+费用推断（未声明变量的 mod 卡）
    if (card.Type == CardType.Attack)
    {
        int cost = card.EnergyCost.Canonical;
        // 粗粒度经验值：1 费 ≈ 6-8 伤害，2 费 ≈ 10-12，3 费 ≈ 14-16
        int estimatedBase = cost switch
        {
            0 => 3,
            1 => 7,
            2 => 11,
            3 => 15,
            _ => 8 + cost * 3,   // X>3 按线性外推
        };
        int strength = player.Creature.GetPowerAmount<StrengthPower>();
        return Math.Max(estimatedBase + strength, 0);
    }

    return 0;  // Skill/Power 通常不打伤害
}
```

> **精度**：经验值是 STS2 费用-伤害曲线的粗略近似（不含附魔/遗物修正），但足以区分"0 伤害的废牌"和"有伤害的攻击牌"——这正是评分函数最需要的粒度。

**对策 2：基于命名空间的 mod 牌效果推断（解决缺口 2）**

```csharp
private static bool HasEnergyGenerationEffect(CardModel card)
{
    // 先查原版白名单（已有逻辑）
    if (ENERGY_GEN_CARDS.Contains(card.Id.Entry)) return true;

    // 再按 mod 卡通用特征推断：
    // mod 卡命名空间不是 "MegaCrit.Sts2.Core.Models.Cards" 的即为 mod 卡
    if (!IsVanillaCard(card))
    {
        // mod 卡的 Type=Skill + 能量相关关键词/效果：
        // 保守策略——如果 cost=0 且是 Skill，大概率有资源产出效果
        if (card.EnergyCost.Canonical == 0 && card.Type == CardType.Skill)
            return true;
        // 更激进的：按 ID 包含能量相关字符串（"energy", "power", "charge"等）
        string idLower = card.Id.Entry.ToLowerInvariant();
        if (idLower.Contains("energy") || idLower.Contains("power") || idLower.Contains("charge"))
            return true;
    }
    return false;
}
```

> **准确率**：约 70-80%——0 费 Skill 大概率有资源产出但也有例外（0 费格挡），误判的后果是给不该加分的牌加了 15 分，偏差可控。

**对策 3：运行期记录 mod 卡的出牌效果（解决缺口 1+3，进阶方案）**

对无法预知效果的 mod 卡，做一次"试打采样"：

```
首次遇到某张 mod 卡 → 出牌后记录：
  { cardId, type, cost, 实际造成的伤害(来自 DamageResult), 实际获得的格挡 }
存入本次 run 的 CardEffectCache（内存，不持久化）
后续再遇到同一张卡 → 用缓存的实测值替代推断值
```

**实现要点**：
- Hook `CardCmd.AutoPlay` 的 postfix，读返回的 `DamageResult` 记录实际伤害
- 不读 `DamageResult` 本身（它是内部类型），改用 `Creature.CurrentHp` 变化量做黑盒测量——出牌前后目标 HP 差即伤害
- 缓存条目有限（本次 run 最多几百张不同牌），内存占用可忽略

> **与药水目标选择器的关系**：`LocalWakuuTargetedCardSelector` 已有类似的"挑选函数"模式（灰水选状态牌、赌徒选打击等），卡效果缓存可以复用其白名单思路，只是换成运行期填充而非编译期硬编码。

#### 18.8.3 兼容性层级总结

```
原版卡（MegaCrit 命名空间）：
    DynamicVar ✅ → 精确伤害/格挡值
    白名单 ✅ → 产能量/抽牌精准识别
    SkadaHelper ✅ → 社区统计

声明了 DynamicVar 的 mod 卡：
    DynamicVar ✅ → 精确值
    白名单 ❌ → 推断层（命名空间+特征）
    SkadaHelper ❌ → 跳过

未声明 DynamicVar 的 mod 卡：
    DynamicVar ❌ → 费用经验值推断（±30%）
    白名单 ❌ → 推断层
    SkadaHelper ❌ → 跳过
    运行期缓存（首次出牌后修正）→ 第二回合起精确
```

**核心保证**：mod 卡在最差情况下（无变量声明、无白名单、无社区统计）不会比最左更差——推断值 + 类型基础分已经提供了合理的排序信号，而最左策略对 mod 卡同样没有任何智能。

### 18.9 从人类打牌中学习（个人偏好记录器）

> 解决问题：mod 卡机制太离谱，不能套评分框架——直接学"我在这种场面下打了什么牌"。

#### 18.9.1 设计思路

记录人类**手动出牌时的完整场面快照**，构建"情境→偏好"映射。瓦库决策时查表：如果当前场面与某条历史记录高度匹配，优先打同张牌。

**关键区分**：本节记录的是**人类手动打牌**（`EnqueueManualPlay`），不记录瓦库自动出牌——后者是我们要替代的决策，不应污染学习数据。

#### 18.9.2 挂点：CardManualPlayContextPatch

已有的 `CardManualPlayContextPatch` prefix 在人类出牌前触发，拿到：
- `card.Owner`（谁打的牌）
- `card.Id.Entry`（打的什么牌）

需要**增加 postfix**，在出牌动作完成后记录完整快照：

```
触发时机：PlayCardAction.ExecuteAction 之后（牌已真正打出，效果已结算）
         或者更早：EnqueueManualPlay 之后（牌已入队、手牌已变化）
         → 推荐 EnqueueManualPlay postfix，此时场面尚未被出牌效果改变
```

#### 18.9.3 快照结构（`CardPlayRecord`）

```csharp
internal sealed class CardPlayRecord
{

    public string CardId;             // card.Id.Entry（"Strike", "东方Project_CardName" 等）
    public string CardFingerprint;    // 卡牌指纹（见 18.10，用于版本校验）

    // ── 场面快照（出牌瞬间）──
    public int PlayerHp;
    public int PlayerMaxHp;
    public int PlayerBlock;

    public int HandSize;              // 手牌数（总）

    public int EnemyMinHp;            // 最低血敌人（简化集火信息）
    public int EnemyMaxThreat;        // 最高威胁意图伤害
```

**"学习价值"判定**：

#### 18.9.4 存储与查询

**存储**：JSON 文件 `%APPDATA%\SlayTheSpire2\vakuu_play_history.json`，按角色+卡牌 ID 分桶：

```json
{
  "Strike": [
    { "fingerprint": "a3f2...", "energy": 3, "hpRatio": 0.8, "enemyCount": 2, "round": 3, ... },
    { "fingerprint": "a3f2...", "energy": 1, "hpRatio": 0.4, "enemyCount": 1, "round": 7, ... }
  ],
  "东方Project_灵符「灵击」": [
    { ... }
  ]
}
```

**查询（瓦库决策时）**：

```
输入：当前场面快照（TurnContext + 手牌列表）
对每张可出牌：
  1. 查该 cardId 的所有历史记录
  2. 用余弦相似度 / 简易加权距离匹配当前场面
     - 权重：hpRatio(0.3) + energy(0.25) + enemyCount(0.2) + round(0.15) + threat(0.1)
  3. 取相似度最高的 N 条记录
  4. 如果 60%+ 的高相似记录都选了这张牌 → 标记为"偏好牌"
输出：偏好牌列表（可能 0 张 = 无匹配历史，回退评分框架）
```

> **简化实现**：一期不做余弦相似度——改用离散化分桶：`hpRatio` 分 4 档（满/高/中/低），`energy` 分 3 档（充裕/刚好/紧张），`enemyCount` 直接匹配，`round` 分 3 档（前/中/后期）。分桶匹配的精度足够（STS2 的场面组合空间有限），实现成本极低。

#### 18.9.5 与评分框架的集成

```
瓦库出牌决策优先级：

① 个人偏好记录（18.9）：高相似场景下人类总是打某张牌 → 直接用
    ↓ 无匹配 / 样本不足
② 评分框架（18.2）：TurnContext + ScoreCard 排序
    ↓ 评分框架无信号（mod 卡 DynamicVar 读不出）
③ 最左兜底
```

**关键约束**：个人偏好记录只影响**选择哪张牌**，不影响**目标选择**——目标选择仍走 18.2.6 的智能逻辑（击杀优先/集火），因为人类的目标选择在出牌时已经做了（`EnqueueManualPlay(target)` 带了目标参数），可以同时记录。

#### 18.9.6 冷启动与数据积累

| 阶段 | 行为 |
| --- | --- |
| 首局（无历史） | 完全依赖评分框架 + 最左兜底，同时开始记录人类操作 |
| 5-10 局后 | 热门原版卡已有足够样本（"Strike 在低血时总不打"之类） |
| 10+ 局后 | mod 卡也开始积累偏好数据（前提：人类确实在用手动出牌而非全托管） |
| 全托管无真人 | 无数据积累（此时完全依赖评分框架 + 推断层） |

> **纯托管模式的局限**：如果两个角色都是瓦库（全自动），没有任何人类打牌输入，个人偏好记录器永远是空的。此时退化为评分框架决策——这正是评分框架存在的意义。

### 18.10 卡牌指纹与版本校验

> 解决问题：游戏/mod 更新后同一张卡数值变了，旧的学习数据不应该继续使用。

#### 18.10.1 卡牌指纹（Card Fingerprint）

每次记录人类出牌时，同时计算该卡的"指纹"——一组反映卡牌能力的快照字段的哈希：

```csharp
internal static string ComputeCardFingerprint(CardModel card)
{
    // 拼接：Id + 费用 + 基础伤害 + 基础格挡 + 关键词 + Type
    var sb = new StringBuilder();
    sb.Append(card.Id.Entry);
    sb.Append('|');
    sb.Append(card.EnergyCost.Canonical);
    sb.Append('|');
    sb.Append(card.DynamicVarSet?.Damage?.BaseValue ?? 0);
    sb.Append('|');
    sb.Append(card.DynamicVarSet?.Block?.BaseValue ?? 0);
    sb.Append('|');
    sb.Append(card.Type);
    sb.Append('|');
    // 关键词排序后拼接（顺序无关）
    foreach (var kw in card.Keywords.OrderBy(k => k))
        sb.Append(kw);
    sb.Append('|');
    sb.Append(card.TargetType);

    // 简单哈希
    using var sha = System.Security.Cryptography.SHA256.HashData(Encoding.UTF8.GetBytes(sb.ToString()));
    return Convert.ToHexString(sha[..8]);  // 取前 8 字节 = 16 字符十六进制
}
```

**指纹包含的信息**：

| 字段 | 变化来源 | 影响 |
| --- | --- | --- |
| `Id.Entry` | 游戏改名卡牌 | 完全不同的卡，旧记录自动不匹配 |
| `EnergyCost.Canonical` | 平衡性调整费用 | 费用变了 → 出牌时机完全不同 |
| `Damage.BaseValue` | 平衡性调整伤害 | 伤害变了 → 击杀窗口计算不同 |
| `Block.BaseValue` | 平衡性调整格挡 | 格挡变了 → 防御价值不同 |
| `Type` | 极少变化（攻击→技能） | 类型变了 → 评分框架基础分不同 |
| `Keywords` | 增减关键词（如加 Exhaust） | 关键词变了 → 策略完全不同 |
| `TargetType` | 极少变化 | 目标类型变了 → 目标选择逻辑不同 |

#### 18.10.2 校验时机

**记录时**：写入 `CardFingerprint` 到 `CardPlayRecord`。

**查询时**：重新计算当前卡牌的指纹，与历史记录的指纹对比：

```csharp
string currentFingerprint = ComputeCardFingerprint(card);
int validCount = 0, staleCount = 0;

foreach (var record in history[cardId])
{
    if (record.CardFingerprint == currentFingerprint)
        validCount++;     // 指纹匹配，记录有效
    else
        staleCount++;     // 指纹不匹配，卡牌已改动，跳过
}

if (staleCount > 0 && staleCount == history[cardId].Count)
{
    // 该卡所有历史记录全部过期 → 清除，从零开始积累
    LocalMultiControlLogger.Info(
        $"卡牌 {cardId} 指纹已变化，清除 {staleCount} 条过期记录");
    history.Remove(cardId);
}
```

#### 18.10.3 游戏版本指纹

除了卡牌级指纹，还需记录**游戏版本**——同一张卡在不同游戏版本下可能有全局规则变化（如"力量不再加成多段攻击"），这种变化不体现在单卡属性里：

```csharp
internal static int ComputeGameVersionHash()
{
    // 读取游戏 DLL 的编译时间戳 或 release_info.json 的 commit hash
    // 简化方案：用游戏 assembly 的 metadata version
    var gameAsm = typeof(CardModel).Assembly;
    return gameAsm.GetName().Version?.GetHashCode() ?? 0;
}
```

**校验逻辑**：如果 `record.GameVersionHash != currentGameVersionHash`，该条记录视为潜在过期（不直接删除，但降权——相似度乘 0.3 系数）。

#### 18.10.4 数据清理策略

```
每次启动时：
  1. 加载 vakuu_play_history.json
  2. 逐条校验指纹 → 移除过期条目（指纹不匹配的）
  3. 总条目数 > MAX_RECORDS (5000) 时，按时间戳淘汰最旧的
  4. 写回文件

运行期：
  每局结束后写盘一次（避免频繁 IO）
  单局内只写内存
```

1. **只出决策、不执行**。大脑返回"下一步做什么"，执行仍走 `LocalWakuuRelicRuntime` 既有链路
   （`PushSelector` 作用域 + `CardCmd.AutoPlay` + 上下文钉住 + 看门狗）。大脑**禁止**自己调用
   `TryManualPlay` / `AutoPlay` / `EnqueueManualUse` —— 否则绕开我们所有的串行化与视觉守卫。
2. **同步快路径 + 异步计划路径分离**。主循环每轮迭代调用的路径必须同步、无 UI 依赖、绝不阻塞主线程；
   异步求解器一律走"整回合计划 + 状态指纹校验"模式（见 21.3.2 的 `TryPlanTurn`）。
3. **三级降级**：大脑异常/超时 → 回退 `HeuristicWakuuBrain` → 再失败 → 最左兜底。
   与 §8.4.1 的"个人记录 → 社区统计 → 兜底"决策链同构，只是这里是**执行层**的三级。
4. **不改第三方 dll、不编译期引用**：适配器全部用 `AccessTools.TypeByName` 反射，集中在单一文件，
   失效即静默降级（参照 §8.2 的 SkadaHelper 口径）。
5. **归属者显式化**：所有入参带 `Player`，禁止任何实现内部用 `LocalContext.GetMe` —— 瓦库是后台角色，
   `GetMe` 在我们的多控环境下语义漂移（这正是 CombatSolver 无法直接用于瓦库的根因）。

#### 21.3.2 接口定义（设计稿）

```csharp
// Scripts/Runtime/WakuuBrain/WakuuDecisionContext.cs
internal readonly struct WakuuDecisionContext
{
    public Player Wakuu;                    // 决策归属者（可能是后台角色，绝不用 LocalContext.GetMe 代替）
    public ICombatState Combat;
    public IReadOnlyList<CardModel> Hand;
    public int Energy;
    public int TurnNumber;
    public int PlayedThisTurn;              // 本回合已打出张数（供护栏与调试）

}

// Scripts/Runtime/WakuuBrain/WakuuPlannedAction.cs
internal enum WakuuActionKind { PlayCard, UsePotion, EndTurn, HandOffToHuman }

internal readonly struct WakuuPlannedAction
{
    public WakuuActionKind Kind;
    public CardModel? Card;                 // PlayCard
    public Creature? Target;                // 目标（Kind=UsePotion 时为药水目标）
    public PotionModel? Potion;             // UsePotion
    public int PotionSlot;
    public string Reason;                   // 仅用于日志/覆盖层
    public bool Confident;                  // false → 记日志并考虑降级

internal interface IWakuuCombatBrain
{
    string Id { get; }
    bool IsAvailable { get; }                                   // 依赖是否就绪（CombatSolver 当前恒 false）

    // 快路径：主循环每轮迭代前调用。必须同步、无副作用、不产生 UI。
    bool TryDecideNext(in WakuuDecisionContext ctx, out WakuuPlannedAction action);

    // 计划路径：整回合批量计划。实现可先同步返回 false（=不支持），将来异步求解器走这里。
    bool TryPlanTurn(in WakuuDecisionContext ctx, out IReadOnlyList<WakuuPlannedAction> plan,
                     out string planFingerprint);

    // 派生选牌作答：给出这一步期望选中的牌（返回 false 则交既有选择器策略）。
    bool TryAnswerCardChoice(in WakuuDecisionContext ctx, IReadOnlyList<CardModel> options,
                             int minSelect, int maxSelect, out IReadOnlyList<CardModel> chosen);

    void OnCombatBegin(Player wakuu);
    void OnTurnBegin(in WakuuDecisionContext ctx);
    void OnCombatEnd();
}
```

**计划指纹（fingerprint）**：借鉴其 `ContinuationStamp` 思路，用一个廉价字符串刻画"计划所基于的战场状态"：
`回合数 | 能量 | 瓦库HP/格挡 | 手牌 id 串（有序）| 存活敌人 id+HP+格挡 | 敌人数`。
主循环每次执行计划中的下一步之前重算指纹，不一致即整份计划作废 → 重新 `TryPlanTurn` 或降级快路径。
这把我们从"看门狗只能熔断重试"（十八节现状）升级为"能察觉实机偏离预期"。

### 21.4 战斗效果覆盖对齐表（瓦库 × CombatSolver）

把"瓦库在战斗中真正会碰到的效果"逐项与它的处理方式对照。目标不是照抄，而是**找出我们从未系统考虑过的边界**。

#### 21.4.1 对照表

| # | 瓦库要处理的效果面 | 瓦库现状 | CombatSolver 做法 | 差距与判断 |
| --- | --- | --- | --- | --- |
| 1 | 主循环出牌选择 | `Hand.Cards.FirstOrDefault(CanPlay)`（最左） | Beam 搜索整回合路线，终局按**生存 > 确认胜利 > 战损 > 药水 > 卖血 > 敌方残余**排序 | 差距最大项。但自研同等能力不现实 → 走 21.3 接口，默认启发式 |
| 2 | 出牌派生选牌（发现/消耗/复制/变化/锻造/弃牌/牌堆） | `LocalWakuuStrategySelector`(first/last/random) + `LocalWakuuTargetedCardSelector` + `LocalWakuuSmithSelector`，在 `PushSelector` 作用域内兜底 | 计划内携带 `PlanCardChoice`，部署时用 `NativeChoiceSession` 按"来源+效果+卡牌语义状态"作答 | 机制等价。它多了**按语义状态匹配**与"嵌套选择顺序"，我们靠策略选择器，够用 |
| 3 | 回合开始选牌（工具箱/暴政/熵/保暖手套/酒狐初始遗物等） | `CardSelectWakuuTurnStartAutoAnswerPatch` **仅覆盖 `FromChooseACardScreen`** | `PlayerTurnSetupCoordinator` 接管 `SetupPlayerTurn` + `RunAutoPrePlayPhase`，搜索后驱动 | 我们只补了酒狐一种入口；`FromSimpleGrid` 类（如非想天则）仍靠安全网。其开发笔记给出**回合开始流水线 6 阶段**：`BeforeSideTurnStart → AfterEnergyResetLate → BeforeHandDraw → AfterPlayerTurnStart → AfterSideTurnStart → AfterSideTurnStartLate`——**正好印证我们十九节的时序结论**（酒狐挂在 `AfterPlayerTurnStart`，此时我们的选择器尚未压栈） |

| 7 | 结束回合与跨回合 | 看门狗 + `StaleCombatActionJanitorPatch` + 敌方就绪补齐 | 结束前**按实机怪物/Power/格挡/意图/额外回合判定复核本轮风险**，若将死亡或掉血高于路线预计则暂停 | 我们结束回合是无条件的。可加"致死风险时交真人"护栏（低优先） |

#### 21.4.2 我们此前从未系统考虑过的边界（按优先级，来自其开发笔记实证）

1. **自动出牌/自动从抽牌堆出牌的嵌套选择**（#4）：至少有 8 类卡路径会漏答。我们靠全局 selector 兜住，
   但应在回归清单里加一条"瓦库打出 横祸/破灭/骚动/蒸馏混沌 等自动出牌卡，观察是否被卡住或选牌错位"。
2. **阵容中途变化**（#8）：召唤/逃跑/Osty/死亡复活后，我们的"第一个可打敌人"和"敌人全灭"判定可能失效。
3. **局内生成卡的入场联动**（#9）：生成牌可能立刻被 Power 联动影响，我们的选择器/评分看不见。
4. **同类型多实例 Power**：其问题包曾因"持有者+Power 类型"作唯一键，遇到两份 `ToricToughnessPower` 直接异常。
   我们用 `GetPowerAmount<T>()` 汇总，不会崩，但**语义是"总层数"而非"每份实例"**——若将来做评分需知悉。
5. **结算顺序细节**：扣费在卡牌效果前；空手检查在牌进入结果牌堆后；药水顺序为
   `槽位移除 → 使用前监听 → 效果/选牌 → 使用后监听 → 空手检查`；死亡阻止后仍 0 HP 时按原版递归（上限十次）。
   我们的 `LocalWakuuPotionAutoUse` 直调 `OnUseWrapper`，建议对照该顺序核一遍。
6. **卖血预算**：普通/精英/Boss 卖血硬阈值 `5/10/15`，且第一二幕 Boss 胜利后回血 → 放宽卖血。
   我们的瓦库**完全没有"卖血上限"概念**，只有致死线判断。
7. **不要用单一线性总分决定路线**：其 `BeamRetentionPolicy`（中间排序，保多样性）与 `FinalPlanOrdering`
   （终局排序）明确分离，且拒绝合并成一个线性总分——**我们 18.2.4 的 `ScoreCard` 正是线性总分**。
   若将来启用评分，这是已知的理论缺陷（当前量级可接受）。

#### 21.4.3 对比后确认"不用改"的（我们已有的隐式优势）

- **全局选择器兜底**：`PushSelector(LocalWakuuStrategySelector)` 作用域内，所有 `From*` 派生选牌被程序化作答，
  等价于它的 `NativeChoiceSession`，且**顺带覆盖了原版自己会漏的自动牌嵌套选择**（#4）。
- **后台化 + 安全网**：`LocalWakuuSafetyNet` 的"超时切前台+提示"是它没有的能力（它遇到未支持边界只能停止并提示卸载 mod）。
- **mod 内容覆盖**：我们为酒狐/古明地恋/污浊等逐个做过定向补丁，它在这些场景直接初始化失败。
