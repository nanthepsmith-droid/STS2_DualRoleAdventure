当前代码里**已经不是**通过给原版「低语耳环 WhisperingEarring」实现托管，而是有一个本 mod 自建遗物：

| 文件 | 作用 |

### 1.2 当前的"自动切换"共有两层

1. **回合循环强制切前台**（防止后台角色 UI/上下文错乱）：
   - `CombatManagerTurnHookForegroundPatch.cs`：`SetupPlayerTurn` / `DoTurnEnd` / `FlushPlayerHand` 三个钩子前切到对应角色；
   - `HookEnqueueForegroundPatch.cs`：Hook 动作入队瞬间切到 owner（如 Mini-Hakkero 选牌）；
   - `CardSelectForegroundSwitchPatch.cs`：选牌 UI 弹出时切人。
2. **瓦库出牌前后的主动切视角**：
   - `LocalWakuuRelicRuntime.EnsureWakuuPerspective`（出牌前切到瓦库）；
   - `RequestAutoSwitchToNonWakuuOncePerRound`（看完门狗跑完登记切回非瓦库）。

### 1.3 已经验证过的关键技术事实

- **"逻辑 owner 与前台显示分离"是可行的**：`RunWatchdogAsync` 里已经实现了临时换 `LocalContext.NetId` + `SetCurrentSenderId` 再恢复的模式（LocalWakuuRelicRuntime.cs:290-291, 310-314）。

- **战斗同步等待已被禁用**：`OnRunLaunched` 中 `CombatStateSynchronizer.IsDisabled = true`，后台角色不会被同步屏障卡住。
- 游戏自带**全局卡片选择器栈** `CardSelectCmd.PushSelector`（sts2src `CardSelectCmd.cs`）：selector 激活时所有 `FromHand/FromSimpleGrid/FromChooseACardScreen/...` 以及 `CardReward.OnSelect` 的选牌 UI 全部被绕过，改为程序化作答。原版低语耳环就是用它包住自动出牌循环的（`VakuuCardSelector`，行优先取最左）。

## 二、逐项需求可行性分析

### 需求一：【瓦库形态】遗物（替代低语耳环方案）—— ✅ 可行性高，大部分已存在

| 子项 | 结论 |
| --- | --- |
| 新增遗物【瓦库形态】 | 已存在（`LocalWakuuStarterRelic`），只需改名 |
| 描述"让瓦库玩算你赢了" | `LocalWakuuRelicLocalization.InjectLocalization` 里改三行字符串即可，含 `title/description/eventDescription/flavor` 四个键 |
| 低语耳环的 +1 能量 | 已实现（`ModifyMaxEnergy`），无需动 |

**存档兼容性**：遗物 id 不变、只改本地化文本，旧存档已发放的遗物不受影响，无需迁移。

### 需求二：战斗内全量自动出牌 + 后台托管 —— ⚠️ 可行，但是本次改动中风险最高的部分

#### 2a. "确保所有出牌都能自动出"

- 现状硬上限 `MaxCardsToPlay = 13`（照抄原版 `WhisperingEarring.maxCardsToPlay = 13`）。改为"循环直到手牌无可出牌"，并加防死循环护栏（迭代上限 + 连续无进展熔断），**可行且低风险**。
- X 费卡：现有 `SpendResources()` 先扣光能量 + `AutoPlay(skipXCapture: true)` 的组合正确（X=实际花费），无需改。
- 出牌过程中衍生选择（发现/回收/选牌等）：由 `PushSelector(new VakuuCardSelector())` 作用域兜底，原版同机制，已验证。
- 手牌在循环中途增加（抽牌效果）：循环每轮重新查询手牌，天然覆盖。
- 主要熔断条件 `TryGetAutoplayUnsafeReason` 检查的是**前台** `NCombatUi.Hand.InCardPlay/IsInCardSelection`——后台化之后语义恰好变成安全护栏（真人正在拖牌时暂停瓦库出牌，看门狗稍后重试），保留即可。

#### 2b. "检测到瓦库形态就不切换过去，让它后台自动选"

**结论：可行，且有充分既有证据支撑，但有一处必须解决的硬缺口。**

依据：
- `CardCmd.AutoPlay` 主链路（sts2src `CardCmd.cs:51-131`）基本是模型层操作，UI 触点只有 `OnEnqueuePlayVfx`（可用 `skipCardPileVisuals: true` 跳过）与 `OnPlayWrapper` 内部动画；
- 1.3 节列出的四条既有事实（owner/前台分离、后台 EndTurn、敌方就绪补齐、同步禁用）都是已在实机验证过的。

需要的改动面：
1. `EnsureWakuuPerspective` 移除或旁路（不再切前台）；
2. 五个切前台补丁（`SetupPlayerTurn`/`DoTurnEnd`/`FlushPlayerHand`/`EnqueueHookAction`/`CardSelectForegroundSwitch`）增加 `IsWakuuEnabled(player.NetId)` 守卫——**注意守卫必须按 player 粒度，不能整体关掉**，否则影响真人的 Mini-Hakkero 等钩子选牌；
3. `RequestAutoSwitchToNonWakuuOncePerRound` 及相关"瓦库↔非瓦库"切换状态机可以大幅简化甚至退役（不再需要切回来）。

**硬缺口（最大风险点）：自动出牌作用域之外的瓦库交互式钩子。**
全局 `Selector` 只在自动出牌的 using 作用域内生效。瓦库在作用域外触发需要人选牌的效果（例如回合开始/结束遗物的 `FromHand` 选牌）时：
- 若无人切前台、又没有 selector → 给后台角色弹出选牌 UI 且永远没人点 → **软锁**。
- 候选对策：
  - **方案 1（推荐，混合式）**：仅在"瓦库 owner 的交互式 Hook 入队"这一种场景保留一次短暂切前台（即 `HookEnqueueForegroundPatch` 按 owner 是否瓦库决定放行或跳过），其余全部后台。改动最小、风险最低。
  - 方案 2：`EnqueueHookAction` 时若 owner 是瓦库，为该动作包一层临时 selector 作用域。技术上要精确对齐异步动作的生命周期，复杂度高。
  - 方案 3：瓦库存活期间挂持久低优先级 selector —— **否决**。selector 在所有 `From*` 路径中优先于 UI，会连真人玩家的选择一起吞掉。

**表现层残留风险**：后台角色的手牌 `NCard` 节点不存在于当前场景，出牌动画/VFX 相关代码若有未做空保护的路径可能抛异常。缓解：`AutoPlay(..., skipCardPileVisuals: true)` 参数现成；游戏代码普遍有 `?.` 保护；此项必须实机回归验证，属于"能做但要留足测试轮次"的部分。

### 需求三 a：战斗结束后自动领最左边的卡牌奖励 —— ✅ 可行，游戏留了现成口子

游戏源码给出了明确的自动化入口（sts2src `CardReward.cs:183-224 OnSelect`）：

```
if (LocalContext.IsMe(player)):
    if (_currentlyShownScreen != null):  num = await 屏幕等玩家点击
    else:                                num = Selector.GetSelectedCardReward(...)   ← 自动化路径
```

而 `NCardRewardSelectionScreen.ShowScreen` 只在 `TestMode.IsOn` 时返回 null（`NCardRewardSelectionScreen.cs:89-94`）——即"不弹屏 + 走 selector 作答"正是游戏测试模式的原生工作方式，我们只需局部复刻：

**实施方案**（在现有 `OfferMergedRewardsGeneratedOnceAsync` 展示奖励屏之前插入）：
1. 遍历合并奖励列表，找出归属瓦库角色的 `CardReward`（`Reward.Player` + `IsWakuuEnabled`，或按遗物判定）；
2. Prefix 补丁 `NCardRewardSelectionScreen.ShowScreen`：当"自动领奖上下文"激活时返回 null（不弹屏）；
3. 用 `ref Task __result` 包装模式（SKILL.md 坑 3）包住 `reward.SelectUnsynchronized()`：内部 `PushSelector(LeftmostSelector)`（`GetSelectedCardReward` 返回 `options.FirstOrDefault()` 即最左边，与原版 VakuuCardSelector 行为一致）；
4. 结算完成后把该奖励从展示列表移除 → 真人看到的奖励界面干净无干扰；
5. `SelectUnsynchronized` 绕过 `RewardsSetSynchronizer`——在本 mod 的单进程回环架构下安全（全员本地玩家，无远端分歧问题；mod 自己的 TestMode 分支就是这么干的）。

附带说明：
- "最左边"= `_cards[0]`；额外按钮类选项（变形等 RewardAlternative）默认不被 selector 选中，符合预期。
- 现有 `CardRewardPatch`（OnSelect 时换上下文到奖励归属者）与本方案正交共存。
- 金币/药水/遗物奖励不在本需求内，保持人工领取（如需扩展见待确认问题 1）。

### 需求三 b：非合作事件自动选最上面的选项 —— ⚠️ 可行，但实现路径要避开一个坑

- **合作事件判定现成**：`EventModel.IsShared` / `EventSynchronizer.IsShared`（投票制，全员投票后 host 抽签）。共享事件直接不碰，交给真人 —— 判定零成本。
- **坑**：不要走 `EventSynchronizer.ChooseLocalOption(index)` 来代选。它会把 `OptionIndexChosenMessage` 通过 `_netService.SendMessage` 发出去，同时本地立即执行 `ChooseOptionForEvent(LocalPlayer, index)`——单进程回环下消息还会被自己的 handler 再消费一次，存在**双重执行**风险；且它绑定的 `LocalPlayer` 是 synchronizer 构造时锁死的 `_localPlayerId`。
- **推荐路径**：直接操作瓦库玩家自己的 `EventModel` 实例：
  ```
  var ev = RunManager.Instance.EventSynchronizer.GetEventForPlayer(wakuuPlayer);
  while (!ev.IsFinished):
      opt = ev.CurrentOptions.FirstOrDefault(o => !o.IsLocked && !o.IsProceed)
      if (opt == null) break          // 复杂局面，留给真人
      await opt.Chosen()              // StateChanged → 界面自然刷新
  ```
  这与 UI 点击最终执行的 `eventOption.Chosen()`（`NEventRoom.OptionButtonClicked` → `ChooseOptionForEvent` → `Chosen()`）是同一落点，只是跳过消息层。
- **Proceed（离开事件）不自动点**：现有的"双角色都完成才允许 Proceed"拦截补丁（`NEventRoomOptionButtonPatch`）天然兼容——瓦库侧自动完成后，真人点 Proceed 即可直接走。
- **多页事件**（选完后出新选项）：上面的 while 循环天然覆盖。
- **必须设排除/中止规则**（否则有软锁风险）：
  - 会导致事件战斗的选项（`EnteringEventCombat`）；
  - 自定义小游戏事件（典型：水晶球 CrystalSphere——其完成回调要求 `owner == LocalContext.GetMe`，且 mod 为它修了三个软锁陷阱，绝不能自动乱选）；
  - 涅奥（Neow）开局奖励是否纳入自动化 → 见待确认问题 3。
  - 建议：一期用黑名单（按 `EventModel.Id` 或"选项触发战斗/小游戏即停"），命中即冻结该事件等真人处理。
- **触发时机**：进事件房后（现有 `NEventRoom.RefreshEventState` postfix 附近）延迟触发 + 重试；与 `RefreshEventRoomForControlledPlayer` 的按人重建流程（`UseSingleEventFlow=false`）兼容性需要实机验证。

### 需求四：概率记录 mod + 瓦库智能选择 —— ✅ 可行，工作量最大，建议独立分期

#### 数据采集（记录真人选择）
- 卡牌奖励：hook `CardReward.OnSelect` 的结果分支（已有 `CardRewardPatch` prefix/postfix 骨架可复用），记录 `{幕数(1/2/3), 首次/重复抓取, 三张候选卡的 key, 实际选择的 index}`。幕数可取 `runState` 当前层信息；候选 key 用排序后的卡牌 Id 串。
- 事件选项：hook `NEventRoomOptionButtonClicked`（真实点击才记录，天然排除瓦库代选），记录 `{eventId, 页码, 选项数, 选择的 index}`；`option.IsProceed` 的点击不计入。
- 排除瓦库：按 `reward.Player` / `event.Owner` 的 `IsWakuuEnabled` 过滤——现成 API。
- 存储：JSON 持久化（Godot `user://` 目录，即 `%APPDATA%\Godot\app_userdata\...` 下），启动时加载、每次记录即时写盘。技术上是普通文件读写，无风险。

#### 右下角概率显示（游玩中）
- 卡牌奖励屏：`NCardRewardSelectionScreen.RefreshOptions` 之后向 `_cardRow`/根 Control 注入一个小 Label（Godot 运行时 new Control + 设置锚点右下），mod 里已有同类先例（`NRewardButtonLabelPatch` 打角色标签、`LocalSimpleTextButton` 自绘按钮），**UI 注入路子已趟通**。
- 事件房：`Layout.AddOptions` 后同理注入。
- 显示内容：当前候选组合下每个选项的历史选择率（样本不足时显示"—"之类占位）。

#### 瓦库智能选择
- 领奖/选事件时查表：在该情境 key 下取历史选择率最高的项；并列最高按配置取"随机"或"最左"（一个常量开关的事）。
- 无记录时的兜底：退化为需求三的最左/最上策略。

#### 独立 mod vs 内置模块（重要决策点）
- 用户设想"另外写一个 mod"。技术上两种都可行：
  - **独立 dll mod**：需新的 mod id、json、ModInitializer。注意本机已有"id 冲突改名"教训（`DualRoleAdventurefixed`），新 mod 必须用全新 id；且与本 mod 有版本配套关系（读同一份概率表），发布时要联动。
  - **本 mod 内置模块 + 开关**（推荐）：部署/版本/日志排查都简单，概率功能用配置项启停，将来想拆随时能拆。
- 无论哪种，**记录器与瓦库智能选择的接口边界要清晰**（一张概率表 + 一个查询函数），方便日后拆分。

## 五、待确认问题（已于 2026-08-24 全部拍板）

   ✅ **已定**：金币、遗物自动领。药水暂不自动领（栏位有限 + 瓦库目前不会用药水）。

## 六、边界场景与第三方内容冲突分析（2026-08-24 增补二）

### 6.1 原版低语耳环 × 瓦库形态 同局共存

现状：`WhisperingEarringPatch` 目前是**无条件放行**的空 Prefix（`return true`），即瓦库角色若在局内又拿到了原版低语耳环（Ancient 稀有度，可获取），两个遗物的 `AfterAutoPrePlayPhaseEnteredLate` 都会触发。

冲突面分析：
- **第一回合双触发**：原版耳环最多自动打 13 张；瓦库形态循环打到无牌可出。先执行者把手牌打完后，后执行者查手牌为空自然空转退出——**不会死锁、不会重复出牌**；
- **选择器栈**：两处都是 `PushSelector` 的顺序 using 作用域，串行进出，无叠加冲突；
- **表现冗余**：可能出现双份瓦库台词（TalkCmd.Play）/双遗物闪光，纯观感问题；
- **能量叠加**：两个遗物的 `ModifyMaxEnergy` 各 +1，合计 +2 最大能量——数值膨胀属于玩法取舍，不是 bug。

**建议处理**：瓦库角色持有【瓦库形态】时，压制原版耳环的自动出牌钩子（**保留**其 +1 能量——那是另一个 hook，不受影响）。实现上给现有补丁加 `Player player` 参数 + `ref Task __result` 短路模式（SKILL.md 坑 2），条件命中返回 false。低风险小改动，纳入 Phase 1。

### 6.2 交互式选牌效果的通用判定规律

任何"需要玩家做选择"的效果，按实现管线分两类：

**A 类 —— 走游戏标准选牌管线 `CardSelectCmd.From*`**（FromSimpleGrid / FromHand / FromCombatPile / FromDeckForUpgrade / FromChooseACardScreen 等）：
- **在自动出牌作用域内**（全局 VakuuCardSelector 生效）：不弹 UI，自动按行优先取前 maxSelect 张解决。min/max 约束由管线自身校验（例如"15 张选至少 4 至多 15"→ `Take(15)` 取满即合法）；连 `RequireManualConfirmation`（需点确认的）也会被 selector 分支直接绕过（sts2src `CardSelectCmd.cs` 中 `else if (Selector != null)` 分支优先于确认逻辑）；
- **在作用域外**：正常弹 UI。若此时前台是非瓦库角色而选择归属者是后台瓦库 → 无人点击 → **软锁**。

**B 类 —— mod 自绘选择 UI，不走 CardSelectCmd**：我们的守卫完全看不见，无论前后台都可能卡住（注：这一风险在**当前版本的 mod 上同样存在**，并非本次改动引入）。

### 6.3 用户列举案例逐一归类

| 案例 | 管线推测 | 触发时机 | 初步判定与风险 |
| --- | --- | --- | --- |
| 古明地恋·弹幕的墨迹测试（15 张选 ≥4 ≤15 后确认） | 待实机验证；若是自绘 UI 则 B 类 | 出牌结算中 | A 类则作用域内自动全取 15 张（约束合法），语义是否合意看效果本身；B 类则依赖安全网兜底 |
| 古明地恋·DNA 的瑕疵（强制结束恋的本回合，下回合恋与玩家都可出牌，恋也从左到右出牌） | 非选牌类 | 回合结构变化 | 恋的自主出牌由该 mod 自管；**需实测**：它的出牌与我们的看门狗/动作队列交错是否会互相打断，以及"同侧双行动者"是否触发我们切人状态机的误判 |
| 古明地恋·封闭心灵（结束恋的回合 + 要求玩家从牌组选一张永久升级） | A 类（FromDeckForUpgrade 特征吻合） | 恋的回合结束时 | 发生在自动出牌作用域外；若被要求选择的是后台瓦库玩家 → 软锁风险点，靠安全网/混合切换兜底 |
| 东方先古之民·非想天则（战斗开始时 10 张故障机器人卡选 5） | A 类（大概率 FromSimpleGrid） | **战斗开始**（必定在自动出牌作用域之外） | **高风险典型案例**：开局选择若归属后台瓦库必软锁。是"混合策略/安全网"必要性的最有力论据 |
| 观者 mod·预见（从看到的抽牌堆顶决定弃哪几张） | A 类（FromCombatPile 特征吻合） | 出牌中 | 作用域内自动取前 N 张——功能可用但"弃哪些"的语义未必理想；可接受或后续针对性优化 |

共性结论：**用户列的案例全部落在 6.2 的框架内**，没有超出"作用域内自动解决 / 作用域外软锁"的二分法。真正要新做的是下面的安全网。

### 6.4 通用交互安全网（新增设计，建议并入 Phase 1）

后台化之后必须有的兜底机制：

```
触发条件（同时满足）：
  1. NOverlayStack 存在等待玩家输入的屏幕/弹层
  2. 该交互的归属上下文可判定为瓦库玩家（能判则精确判；判不了按保守处理）
  3. 无任何输入持续超过阈值 T 秒
动作：
  → 自动把前台切给该瓦库玩家 + 全屏提示"瓦库遇到需要手动处理的界面"
  → 打高亮日志
效果：把硬软锁降级为"请人工点一下"，同时覆盖 A/B 两类（B 类只有这条能兜住）
```

- 与现有 watchdog/熔断日志体系共用去重键，避免刷屏；
- 阈值 T 建议 8–15 秒（太短会在正常动画期间误报，配合 6.2 的 CanSwitch 守卫防误切）；
- 无法精确判归属时宁可误切到瓦库（人工可见）也不静默卡死。

### 6.5 新增实机回归清单

1. 双遗物局：瓦库形态 + 原版耳环同持，验证第一回合只触发一次接管、+2 能量生效、无双台词（压制生效后应为零原版钩子）；
2. 墨迹测试：瓦库打出该卡 → 观察 15 张是否被自动选取、效果正确入栈；
3. DNA 的瑕疵：瓦库场上有恋 → 连续两回合观察恋与瓦库的出牌交错、无队列死等；
4. 封闭心灵：恋回合结束后升级选牌界面归属判定与弹出行为；
5. 非想天则：带瓦库进战斗 → 开局 10 选 5 是否触发安全网切人提示；
6. 预见：作用域内的弃牌自动决策是否符合最低可玩性；
7. 安全网本身：人为制造一个 B 类弹层（如某 mod 自定义界面），验证超时切人与提示出现、处理后流程继续。

### 6.6 同侧多行动者（古明地恋）与瓦库的出牌权竞争

用户追问："恋和瓦库抢出牌不用管吗"。分层回答：

**已有隔离（无需处理的部分）**：
- 自动出牌循环只遍历 `PileType.Hand.GetPile(relic.Owner)` —— **瓦库形态永远不会替恋出牌**；
- 恋的自主出牌（含她的"从左到右"）由该 mod 自行驱动，与我们不共享决策代码。

**真实竞争面（需要设计应对的部分）**：

| 竞争点 | 表现 | 对策 |
| --- | --- | --- |
| 动作队列交错 | 恋的行动与瓦库自动出牌在同一 PlayPhase 内并发入队，可能交错执行或互相等待 | 实测为主（回归清单 #3）；现有 SelectorScopeGate 串行闸门已有一定保护 |
| 回合结构抖动 | DNA 的瑕疵等强制结束/追加行动者的效果，使熔断条件（CurrentSide/PlayPhase 检查）反复翻转 → 看门狗反复重试 | 看门狗冷却/去重键已有；必要时把"结构异常"计入熔断 |
| 时机窗口抢占 | 全自动秒出可能跳过恋的效果所依赖的玩家先行操作 | 见下面的降级开关 |

**新增降级开关（非默认行为）**："检测到非标准行动者在场（恋等）时，暂停看门狗重启、只保留回合开始的一次性接管"——把节奏交还原时序，作为实测发现抢牌问题后的逃生门。并入 6.4 的开关体系。

## 八、SkadaHelper 集成分析（2026-08-24 增补）

> 背景：创意工坊已有「皮皮军师: SkadaHelper」(v0.8.7, workshop id 3763804482)，
> 内置 404,569 局 v0.107 实战统计快照 + 本地路线模型，纯显示层 mod。
> 已反编译其 DLL 验证集成面（反编译产物在临时目录，不入库）。

### 8.1 公开 API 面（已验证可直接调用）

| 类型 | 可见性 | 说明 |
| --- | --- | --- |
| `SkadaHelper.Scripts.Lite.DataProvider` | **public static class** | 数据入口 |
| `DataProvider.Data` | **public static** `BundleData?` | 当前生效的已校验数据包（缓存→内置→在线刷新） |
| `BundleData.GetCharacter(charId)` / `.GetCard(charId, cardId)` | public | 角色包查询 |
| `CharacterBundle.GetCard(cardId)` | public | → `CardStats`；自动按进阶(A7+)/单人多人切片并逐级回退 |
| `CharacterBundle.GetEvents(eventId)` | public | → `List<EventOptionStats>`；eventId 大写 |
| `CardStats` 字段 | public | `PickRate / WinRate / WinRateSkipped / WinRateHeld / OfferCount / PickedCount / SkippedCount` + 升级、删牌统计（位置/次数/首次胜率） |
| `EventOptionStats` 字段 | public | `Text / Count / WinRate` |

关键实现细节（来自反编译）：
- 卡牌 key = 裸卡 id（自动剥 `+` 升级后缀）；角色 key = `ModelId.Entry` 大写；
- 单人/多人切片判定是 `Players.Count <= 1` —— **本 mod 双人模式会命中 multi 切片**（数据来自线上真人合作局，语境略有偏差但可接受）；
- 切片回退链：当前进阶切片(≥A7) → 全量；multi/solo → 全量。查询永远有兜底值。

### 8.2 推荐集成方式

- **可选依赖 + 反射查询**：`AccessTools.TypeByName("SkadaHelper.Scripts.Lite.DataProvider")` → 读静态属性 `Data`。未安装/未加载时优雅回退到"最左/最上"策略。不做编译期引用（它是可选第三方 mod）。
- **用瓦库玩家自己的角色查表**：不要走它的 `LiteGameContext.CurrentCharacterId`（跟随前台 `LocalContext.GetMe()`，在多控下语义漂移）；直接 `BundleData.Characters[wakuuCharId]` 或 `GetCharacter(wakuuCharId)`。
- **决策信号建议**：
  - 卡牌奖励：主信号 `PickRate`，可选加权 `WinRateHeld - WinRateSkipped`（近似因果增益）；样本量 `OfferCount` 过小则视为无数据；
  - 事件选项：`WinRate` 最高且 `Count` 达阈值者；并列最高走用户开关（默认最左）。

### 8.3 相比原自建记录器方案的优势

1. **样本量碾压**：40 万局社区数据 vs 个人几百次选择，冷启动即有效；
2. **自带胜率维度**：不只是"别人选什么"，还有"选了之后赢没赢"，比纯选择率更强的信号；
3. **零开发量的右下角显示**：SkadaHelper 本身就在卡牌奖励/事件/商店/删牌升级界面渲染统计面板——原需求四的"游玩过程中右下角显示概率"直接由它满足；
4. **别人维护**：随版本更新数据口径，本 mod 不背数据管道包袱。

### 8.4 风险与限制

| # | 风险 | 等级 | 对策 |
| --- | --- | --- | --- |
| 1 | 数据口径 v0.107 vs 当前游戏 v0.111，元环境漂移 | 中 | 接受（作者更新后自动恢复）；决策仅作参考信号，不改变回退策略的正确性 |
| 2 | 事件选项按**文本模糊 Contains 匹配**，语言敏感：若数据集为英文而玩家中文界面，可能匹配失败 | 中 | 实机验证中文环境命中率；未命中时回退最上选项 + 打日志统计命中率 |
| 3 | multi 切片来自线上真人合作局，与本地单人多控语境有偏差 | 低 | 接受；必要时只取全量切片 |
| 4 | 第三方 mod 可能改内部结构（类名/属性名） | 低 | 反射全部集中在单一适配器文件 + 启动探测日志；失效即静默回退 |
| 5 | 合规 | 低 | 只读消费内存中公开 API，不重分发其 dll/数据，不修改其行为；AGENTS.md 的"不改第三方 dll"约束不受影响 |
| 6 | **不含任何 mod 内容**（已反编译确认：`BundleFilters` 仅含版本/进阶/模式/人数四个维度，卡表/事件表为纯原版 id 字典；标准模式数据源决定了 mod 卡牌/事件无 key） | 中 | 查询 miss 一律返回 null → 静默回退最左/最上（无害降级）；mod 环境下原版卡的社区统计参考价值也会稀释，接受其仅为参考信号 |

### 8.4.1 mod 内容缺口的应对：三级决策链

个人偏好记录器（用户设想的 STS1 抓率统计式 mod，可做独立 dll）与本方案**互补而非二选一**——它记录本机实际对局，天然覆盖 mod 卡牌与 mod 事件：

```
① 个人记录器（该情境有足够样本时，最贴合实际环境含 mod 内容）
② SkadaHelper 社区统计（原版内容，大样本）
③ 兜底策略（最左 / 最上，按已定开关）
```

### 8.5 与本 mod 补丁的共存性（已核对双方补丁面）

- SkadaHelper 的补丁全是 **postfix 显示层**（`NCardRewardSelectionScreen.RefreshOptions`、`NEventLayout.AddOptions`、商店/地图/牌组网格），不改游戏状态；
- 本 mod 计划对瓦库奖励**不弹屏**（ShowScreen prefix 返回 null）→ 它的 RefreshOptions postfix 对这些屏自然不触发，互不干扰；
- 事件自动化直调 `EventOption.Chosen()`，不经过 `NEventLayout.AddOptions` 路径 → 无冲突；
- 双 Harmony 同进程共存是常规场景，无风险。

### 8.6 结论

**采纳**：Phase 3 主路径改为"三级决策链"——个人记录（可选，后建）→ SkadaHelper 社区统计 → 最左/最上兜底。SkadaHelper 不支持 mod 内容的限制由兜底策略与个人记录器共同覆盖；原需求四的开发量缩减约七成。

## 九、聪明瓦库：启发式决策升级（2026-08-24 增补三）

> 用户需求原文归纳：
> 1. 消耗类选牌：优先 诅咒 → 状态 → 任务 → 打击 → 防御，再从左到右；
>    复制类选牌：尽量排除这些牌（优先选其余更好的牌），候选全是这类时按倒序 防御 → 打击 → 任务 → 状态 → 诅咒；
> 2. 变化类选牌：优先 打击 → 防御，尽量避开 诅咒/状态/任务；
> 3. 商店：买胜率高的东西、删诅咒/打击/防御；
> 4. 所有瓦库行为加独立开关。
>
> 用户自评"结果还是会打得很烂"——目标是"不犯低级错误"而非最优。

### 9.1 选牌场景识别——关键可行性依据

游戏源码中选牌入口天然可分类（sts2src `CardSelectCmd.cs`），无需猜测 UI 语义：

| 场景 | 游戏管线 | 识别难度 |
| --- | --- | --- |
| 变化（Transform） | `FromDeckForTransformation` —— **专用方法** | ★ 直接按方法区分 |
| 删牌（商店/事件） | `FromDeckForRemoval` —— **专用方法** | ★ 直接按方法区分 |
| 升级 | `FromDeckForUpgrade` —— 专用方法 | ★ |
| 消耗/弃置/复制等手牌与杂项选择 | `FromHand` / `FromSimpleGrid` / `FromChooseACardScreen`（带 `source` 来源模型参数与 prefs 标题 LocString） | ★★ 按 `source` 的类型名 / prefs 标题 loc key 分类；未知来源回退通用策略 |

实现载体：把现在的 `VakuuCardSelector`（无脑取最左）升级为**带场景上下文的优先级选择器**——在自动出牌作用域内拦截所有 `GetSelectedCards` 调用，先判定场景类别再套对应优先级表。

### 9.2 优先级规则表（可配置）

```
场景 = 消耗/删除类（去掉坏牌）:
    Curse > Status > Quest > Strike > 基础防御 > 其余从左到右
场景 = 复制类（复制好牌）:
    首选：非 {Curse/Status/Quest/Strike/基础防御} 的牌，从左到右
    候选全为上述类型时：倒序 防御 > 打击 > 任务 > 状态 > 诅咒
场景 = 变化类（变掉平庸牌、保留特殊牌）:
    Strike > Defend > 其余从左到右；硬排除 Curse/Status/Quest
兜底: 现行"最左"
```

> 实现说明：规则做成数据驱动的优先级表（JSON 或代码常量），每条场景一行即可调整，不影响结构。"候选全是坏牌时倒序"的判定就是普通过滤后集合是否为空，无额外成本。

卡牌类型判定 API：`CardModel.CardType`（Curse/Status/Quest/Attack/Skill）+ 卡 id 白名单（打击/防御的各角色变体如 Strike_Ironclad 需按 `BareCardId` 前缀匹配）。均为公开模型属性，零风险。

### 15.1 根因（实测日志链）

1. 玩家 HEADBUTT（id88）Executing 中击杀最后一敌 → mod 立即胜利结算触发，
   战斗状态翻转 NotInCombat；
2. 游戏 CombatEnded 清理跳过 Executing 状态动作（日志原话 Not cancelling action ... state: Executing）；
3. 该动作随后 PauseForPlayerChoice → Resume 换发新 id89，但已不在战斗，
   CombatPlayPhaseOnly 类型永远不再执行，卡死在队列头部；
4. 后续所有 VoteForMapCoordAction 排在它后面无法执行（ActionQueueSet 找 ready action
   时遇到队首不可执行候选即放弃）→ 点节点只入队不执行、无 vote changed、
   地图自动跟投 postfix 根本不触发 = 用户看到的"瓦库不跟、不自动出发"。

  延迟多轮（750ms×8）扫描各玩家队列，非战斗状态下残留的
  Combat/CombatPlayPhaseOnly 且非 Executing 的动作按游戏原语义 Cancel+移除；
  新战斗开始/退出对局立即停止；单飞防重入。

### 15.3 回归点
